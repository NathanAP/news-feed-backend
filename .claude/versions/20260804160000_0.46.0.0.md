# 0.46.0.0 — Atualização de dependências

## Resumo

Primeira metade da 0.46. Fecha o item "Atualização de dependências / bibliotecas" do ROADMAP; o item
"Revisão" segue aberto e sairá como patches (`0.46.1.0`+), conforme a regra de que alteração causada
pelo revisor sobe patch.

A ordem foi deliberada: **dependências antes da revisão**, para que a revisão leia o código como ele
vai rodar de fato e para que uma quebra de dependência nunca se misture a uma correção de revisão.

O gatilho principal não foi "estar atrasado", foi **segurança**: o `govulncheck` apontava 3
vulnerabilidades com símbolo alcançável pelo nosso código. Depois desta versão são **zero**.

## Método

Linha de base verde antes de tocar em qualquer coisa (`task test-all`, exit 0), e a suíte completa
rodando entre cada bloco, para que uma quebra fosse atribuível a um bloco específico.

## Tier 1 — segurança

| Vulnerabilidade | Módulo | De → Para |
|---|---|---|
| GO-2026-5970 — loop infinito com input inválido | `golang.org/x/text` | v0.37.0 → v0.40.0 |
| GO-2026-5856 — vazamento de privacidade no ECH | Go (stdlib `crypto/tls`) | go1.26.4 → go1.26.5 |
| GO-2026-6061 — RBAC xDS / transporte HTTP2 | `google.golang.org/grpc` | v1.80.0 → v1.83.0 |

O **x/text era o que realmente importava**. O trace passava por `services/rss/discovery.go:125 →
http.Client.Do → norm.Form.*`, ou seja, por **conteúdo remoto de RSS** — input arbitrário, servido por
terceiro, a partir de uma URL que o usuário cadastra. Um loop infinito ali é DoS na goroutine de
descoberta, e colide direto com a regra do `conventions.md` de que "feeds indisponíveis não devem
derrubar a aplicação" (aqui não é indisponibilidade, é feed hostil ou corrompido).

O **grpc foi atualizado por higiene, não por exposição**: os traces do govulncheck eram do tipo
`logger.Print calls fmt.Printf, which eventually calls transport.ClientStream.Close`, que é artefato do
call graph resolvendo dispatch de interface pelo `fmt` — não um caminho que executamos. O grpc entra
via `genai` e `testcontainers`.

**Toolchain sem edição em cascata**: o `go.mod` foi de `go 1.26.4` para `go 1.26.5` e só. O Dockerfile
usa a tag flutuante `golang:1.26-alpine` (pega o patch no rebuild) e o CI usa
`go-version-file: go.mod`. Os três ficam em sincronia por construção, não por alguém lembrar.

**Percalço**: subir o grpc arrastou `cloud.google.com/go/auth` para v0.18.2, que importa um
`gax-go/v2/internallog` sem entrada no `go.sum` — o build quebrou. Resolvido com `go mod tidy`.

## Tier 2 — diretas de baixo risco

`gofeed` v1.3.0 → v1.4.0 · `goose/v3` v3.27.2 → v3.27.3 · `go-retry` v0.3.0 → v0.4.0 ·
`golang.org/x/net` v0.55.0 → v0.57.0 · `genai` v1.62.0 → v1.66.0.

As duas com risco real de quebra foram conferidas antes: o `go-retry` v0.4.0 mantém
`WithMaxRetries(uint64, Backoff)` e `NewExponential` (nossos 3 usos — gemini, openaicompat, discovery —
não mudam), e o `gofeed` v1.4.0 troca `goxpp` por `goxpp/v2` internamente, mas nosso uso é só
`NewParser`/`Feed`/`Item`.

## Tier 3 — `lib/pq`: tentado, revertido, documentado

**Intenção**: remover o `lib/pq`. Ele era dependência direta por um único motivo — o `pq.Array` que o
sqlc emite para `ANY(sqlc.arg(article_ids)::text[])` em `ListArticleOutboundLinksByArticleIDs` (0.45).
Puxar um driver inteiro por uma função de encoding, e ainda o driver que a 0.37 substituiu por pgx,
parecia código morto disfarçado.

**Resultado: não é possível hoje.** O `sqlc.slice()` **é quebrado para o engine postgresql** no sqlc
v1.31.1. O gerado sai assim:

```go
// const:
WHERE article_id IN ($1)                                    // marcador /*SLICE:*/ perdido no render
// corpo:
strings.Replace(query, "/*SLICE:article_ids*/?", ...)       // procura marcador que não existe -> no-op
strings.Repeat(",?", len(articleIds))                       // placeholder `?` é MySQL, não Postgres
```

O `Replace` vira no-op e a query fica com **um** placeholder recebendo **N** parâmetros.

**O detalhe que mais importa desta versão**: isso **compila**, passa no `go vet`, e **passa em todo
teste que envia um único id** — que é exatamente o que os testes diretos do Querier fazem
(`processor_test.go:186` e `:253` passam `[]string{umID}`). Quem pegou foram os testes de integração de
`GET /v1/articles`, que passam a página inteira: 4 falhas com N ids. Sem essa camada, a mudança teria
ido verde para produção e quebrado na primeira notícia com dois links.

**Decisão**: manter `ANY(...::text[])` e o `lib/pq`, atualizado v1.10.9 → v1.12.3. A query ganhou um
comentário explicando o porquê e proibindo explicitamente a "limpeza" com `sqlc.slice`, para ninguém
repetir a tentativa. As alternativas descartadas: escrever nosso próprio encoder de array `text[]`
(reinventar o `pq.Array`, fácil de errar em quoting/escaping/NULL) e migrar o `sql_package` do sqlc para
pgx nativo (desaconselhado pelo comentário do próprio `sqlc.yaml`, e grande demais para esta versão).

Vale registrar a proporção: o `lib/pq` aqui é um **helper de encoding de array**, não um segundo driver
ativo. O driver é inequivocamente o pgx. O incômodo é de convenção, não de arquitetura.

## Roadmap

- **0.47.0.0 criada: migração Fiber v2 → v3.** Estamos no v2.52.14 e o v3 está em v3.4.0 — a única
  dependência uma major inteira atrás. Sem CVE aberto, então é dívida, não incêndio. Superfície medida
  no fonte do v3.4.0 (não na doc): ~58 pontos de edição, 47 deles a troca `*fiber.Ctx` → `fiber.Ctx`.
  O que a doc oficial diz que quebra e **não quebra**: `Context()` continua existindo, só estreitou o
  retorno de `*fasthttp.RequestCtx` para `context.Context` — nossos 88 usos são todos
  `runTx(c.Context(), ...)` e compilam intactos. Detalhes completos na entrada do ROADMAP.
- Removidas de "planos futuros" duas entradas **já entregues na 0.42**: "Preparar ambiente staging +
  production" e "CI/CD". "Cascade de tabelas" marcada como parcial (a 0.45 fez a de
  `article_outbound_links`).

## Como testar

```bash
task test-all
```

Para reproduzir a verificação de segurança:

```bash
go run golang.org/x/vuln/cmd/govulncheck@latest ./...
```

Deve responder `No vulnerabilities found`. As 3 que ele ainda reporta em "modules you require" são de
módulos que não chamamos.
