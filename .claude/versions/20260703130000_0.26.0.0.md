# Versão 0.26.0.0 — subir a aplicação via Docker

**Data:** 2026-07-03

Deixa a aplicação subir por Docker: **API** + **SQLite com interface gráfica** (`sqlite-web`). Ficou
das versões mais simples porque o `modernc.org/sqlite` é **Go puro** — build estático com
`CGO_ENABLED=0`, sem bibliotecas C no runtime.

## Mudanças

### Dockerfile (multi-stage)
- Builder `golang:1.26-alpine` → binário estático (`CGO_ENABLED=0`, `-trimpath -ldflags="-s -w"`).
  As migrações são embutidas (`go:embed`), então nada mais precisa ir pra imagem final.
- Runtime `alpine:3.21` com os **CA certificates copiados do builder** (`/etc/ssl/certs/ca-certificates.crt`)
  em vez de `apk add` — assim o estágio final não depende do mirror de pacotes do Alpine (que pode
  estar bloqueado por firewall/proxy, como aconteceu no teste real). Necessários para o HTTPS de saída
  (Gemini/Groq/RSS). Só o binário `api` no runtime.

### docker-compose.yaml
- Serviço `api`: `build .`, porta 3000, volume `./db:/app/db` (persiste o banco e é compartilhado com
  o host — semear no host reflete no container), `env_file: .env`.
- **Healthcheck** na API via `wget` no `/health` (isento do guard de manutenção → responde 200
  sempre que a app está no ar). Usa **`127.0.0.1`** (não `localhost`): o Fiber escuta IPv4 (0.0.0.0) e
  o busybox resolvia `localhost` para IPv6 (`::1`) primeiro → "connection refused" (pego no teste real).
- **`extra_hosts: host.docker.internal:host-gateway`**: permite alcançar serviços do host (ex.: um
  Ollama nativo). No-op no Docker Desktop; habilita no Linux. Em Docker prefira
  `KEYWORDS_MODE=groq|gemini` — o Ollama do host **não** é alcançável por `localhost` de dentro do
  container.
- Serviço `sqlite-web`: UI do SQLite (dev), configurado pela interface documentada da imagem
  (`SQLITE_DATABASE=news_feed.db` + mount `/data`), **sem** sobrescrever `command` — o scaffold antigo
  passava `command: ["-H", ...]`, que a imagem tentava executar como binário (`exec: "-H" not found`).
  `depends_on: api (condition: service_healthy)` — só abre o banco **depois** que a API subiu e
  migrou, evitando a corrida do primeiro boot.

### Taskfile
- Tasks de Docker migradas de `docker-compose` (v1, EOL) para `docker compose` (v2). `task ds` agora
  faz `up -d --build`. Novo `task docker-full-restart` (`dfr`) = `down` + `up --build`.

### `.dockerignore`
- Mantém o que os builds precisam (fontes Go, `go.mod/go.sum`, `migrations/`, `cmd/` + `examples.json`
  para a imagem de seed) e exclui cruft/segredos (`db/`, `tmp/`, `.env*`, `.git/`, `.claude/`,
  `bruno/`, `tests/`, `*.md`). (Criado antes, na conversa da 0.26.)

## Decisões (simplificações combinadas)
- **Ollama não é containerizado** e o modo `local` não é usado em Docker (resultados fracos e
  desnecessário). Fica como conveniência nativa (`task ls`). `host.docker.internal` disponível caso
  um dia queira.
- **Seed no container: não implementado, por design.** O `db/` é volume bind-mount, então semear no
  host (`task sdfull`) e subir o container é equivalente a semear dentro dele. Item removido do
  ROADMAP pelo usuário.

## Como testar
- `task ds` (ou `docker compose up -d --build`) → API em `:3000`, sqlite-web em `:8080`.
- `docker compose ps` mostra `api` como `healthy`; `sqlite-web` sobe só depois.
- Fluxo dev típico: `task sdfull` (semeia no host) → `task ds` (container lê o mesmo `db/`).
- `docker compose config` valida a orquestração (feito aqui, sem daemon).

## Observações
- Não foi possível rodar `docker build`/`up` neste ambiente (daemon indisponível); o `compose config`
  validou a sintaxe e o comando de build do Dockerfile foi verificado com `go build` idêntico. O teste
  real de subir fica para a máquina do usuário.
- Binário grande (~150 MB) por causa do `modernc.org/sqlite` (tradução do SQLite em Go). Esperado.
- Sem mudança em código Go → suíte de testes inalterada (50 pacotes verdes).
