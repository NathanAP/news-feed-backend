# Versão 0.21.2.0 — modos de keywords (local/groq/gemini) + benchmark via Bruno

**Data:** 2026-06-30

Patch que torna a nomeação de keywords **plugável e comparável** entre três backends, e a rota de
teste prática pra medir cada um direto no Bruno (motivado pela lentidão do SLM local em CPU).

## O que foi feito

- **`KEYWORDS_MODE`** seleciona o backend de keywords (`PROJECT.md` → "Nomeação de palavras-chave"):
    - `local` — Ollama (SLM da stack, `qwen3:4b`) via `openaicompat` @ `OLLAMA_BASE_URL`.
    - `groq` — Groq (serviço online de SLM) via `openaicompat` @ `GROQ_BASE_URL` + `GROQ_API_KEY`,
      modelo em `GROQ_MODEL` (a stack não fixa um).
    - `gemini` — LLM (Gemini `gemini-2.5-flash`) via o cliente Gemini, usa `GOOGLE_API_KEY`.
- **`main.buildKeyworders`** pré-constrói os três modos no startup (cada um com o verbose logger) e
  devolve um `map[modo]Keyworder` + o modo default (`KEYWORDS_MODE`). Pré-construir todos permite a
  troca por chamada sem reiniciar.
- **`openaicompat` ganhou API key** (`NewClient(baseURL, model, apiKey)`) — envia `Authorization:
Bearer` quando setada; local (Ollama) segue sem key, Groq usa a key.
- **Rota de teste turbinada** (`POST /v1/articles/treatment`): body aceita `keywords_mode` opcional
  (local | groq | gemini) que sobrepõe o default **só naquela chamada** → benchmark direto no Bruno,
  sem reiniciar (400 se o modo não existir). A resposta agora traz `keywords_mode`, `treatment_ms` e
  `keywords_ms` pra medir cada etapa. Modelos fixos à stack (local/gemini); `groq` configurável.
- A CRON e o processor usam o keyworder do modo default.
- **Fix (durante o teste):** o `openaicompat` montava `/v1/v1/chat/completions` quando a base já
  terminava em `/v1` (caso do Groq). Agora tolera os dois formatos (base com ou sem `/v1`), com
  teste de regressão.

## Nota sobre grafia

O modo e as envs foram padronizados para **`groq`** (serviço Groq): `KEYWORDS_MODE=groq`,
`GROQ_API_KEY`, `GROQ_BASE_URL`, `GROQ_MODEL`.

## Testes

- `openaicompat`: novo caso garante o header `Authorization: Bearer` quando há API key.
- Rota de tratamento: `keywords_mode` override (200 com o modo escolhido), modo inexistente (400),
  e presença de `treatment_ms`/`keywords_ms`/`keywords_mode` na resposta.
- `go vet ./...` limpo e `go test ./...` sem falhas (tudo via mock; providers reais não entram em CI).

## Como testar (real, prático)

Com o app no ar (`task ls`), no Bruno em _Article Treatment_ adicione ao body:
`"keywords_mode": "local"` e depois `"groq"` e `"gemini"`, comparando `keywords_ms` de cada um. Sem
reiniciar. (Para `groq` precisa de `GROQ_API_KEY` + `GROQ_MODEL`; para `gemini`,
`GOOGLE_API_KEY`.)

## Notas de escala (recap)

- Local em CPU não escala pra volume; `groq` (SLM hospedado) tende a ser sub-segundo. Esse endpoint
  serve justamente pra você escolher o melhor custo/latência/qualidade por benchmark.
