# Versão 0.30.0.0 — nome da fonte + `with_sources` em `GET /v1/feeds/{id}/articles`

**Data:** 2026-07-08

Duas mudanças, pensadas para o client conseguir mostrar a fonte de cada notícia sem uma segunda
chamada.

## 1. Campo `name` em `sources`

- **Migração** (`migrations/20260708123212_add_name_to_sources.sql`): SQLite recusa
  `ALTER TABLE ADD COLUMN NOT NULL` sem default quando a tabela pode ter linhas, então segui o
  padrão já usado duas vezes no projeto (rebuild de tabela: `sources_new` com a coluna, copia,
  dropa, renomeia, recria os índices únicos parciais de `url`/`url_rss`). `down` simétrico. Sem
  backfill — banco local recriado do zero, como combinado.
- **Schema/sqlc**: `schema.sql` (espelho) e `sqlc/queries/sources.sql` (`CreateSource`,
  `UpdateSource` passam a incluir `name`) atualizados, e o código gerado foi produzido rodando o
  `sqlc generate` **real** (binário `v1.31.1` instalado), não mais editado à mão.
- **Camadas**: `SourceController.Create/Update` ganharam o parâmetro `name`;
  `SourceControllerInterface` atualizada; `schemas.SourceResponse`/`CreateSourceRequest`/
  `UpdateSourceRequest` ganharam `Name`; nova constante `schemas.SourceNameMaxLength = 120`
  (espelha `FeedNameMaxLength`); os endpoints `create`/`update` de sources validam `name`
  obrigatório e ≤120 caracteres (400 se violar) e o repassam.
- **Seed**: `cmd/seed/examples.go` (`exampleSource.Name`), `cmd/seed/examples.json` (nome da fonte
  de exemplo) e `cmd/seed/dev_sources.go` atualizados.
- **Testes**: fixtures (`tests/fixtures/source_fixtures.go`) ganharam `Name`; testes unit/
  integração/E2E de `sources` cobrem `name` ausente (400) e muito longo (400), e passam a
  incluir `name` em todo body de criação/edição usado nos demais pacotes de teste que semeiam uma
  source (discovery, cron, articles, articles_feeds, feeds) — por consistência, mesmo onde não era
  estritamente necessário para compilar.

### Efeito colateral: primeira geração real via `sqlc generate`

Até aqui o código em `sqlc/*.go` era escrito à mão imitando o padrão do sqlc (ver `overview.md`).
Esta versão foi a primeira a rodar o `sqlc generate` de verdade, e isso trouxe dois achados que
não têm relação com o campo `name`, registrados aqui para não se perderem:

1. **Rename do modelo da junction table**: o sqlc real deriva `ArticlesFeed` (não `ArticleFeed`) do
   nome da tabela `articles_feeds`. Todos os 8 arquivos que referenciavam `db.ArticleFeed` foram
   atualizados para `db.ArticlesFeed` (rename mecânico; nomes dos nossos próprios tipos como
   `ArticleFeedController` não mudam, só o tipo gerado).
2. **Gotcha de encoding**: um comentário SQL com caracteres **em-dash (—)** na query
   `ListArticlesByFeedForUser` corrompia a geração do sqlc v1.31.1 (truncava a query no meio e
   vazava o texto pro início da constante seguinte) — bug de offset de bytes vs. caracteres do
   parser do sqlc diante de UTF-8 multi-byte antes da query. Removidos os em-dashes do comentário
   (nenhum outro `.sql` do projeto os usava). **Lição prática: evitar em-dash e outros caracteres
   não-ASCII em comentários de `.sql` neste projeto.**
3. Como achado à parte (não corrigido, fora de escopo): `FindCandidateFeedsByKeywords` — que usa
   `json_each(?)` — sempre foi gerada pelo sqlc real com o parâmetro tipado `interface{}` (nomeado
   `jsonEach`), não o `articleKeywords string` que o hand-write usava. Funciona (Go aceita `string`
   como `interface{}`), mas perdeu a tipagem explícita. Fica registrado para uma limpeza futura
   (`sqlc.arg`/`CAST(? AS TEXT)` na query resolveria).

## 2. `?with_sources=true` em `GET /v1/feeds/{id}/articles`

- **Convenção nova** (adicionada por você a `conventions.md`): `with_{tabela_relacionada}=true`
  para popular opcionalmente dados de tabela relacionada; qualquer valor diferente de `true` é
  ignorado silenciosamente (nunca erro).
- **SQL**: `ListArticlesByFeedForUser` passou a sempre fazer
  `JOIN sources s ON s.id = a.source_id AND s.status = 1 AND s.removed_at IS NULL` (seguro: artigo
  ativo garante fonte ativa via cascade da 0.14.1.0), trazendo `name`, `status`, `url`, `url_rss`,
  `created_at`, `modified_at` da fonte (o `id` já vem de `a.source_id`, sem duplicar).
- **Go**: o join roda sempre (barato — chave primária), mas o handler só **mapeia** o campo
  `Source` na resposta quando `?with_sources=true` — evita manter duas queries.
- **DTO**: `schemas.ArticleResponse` ganhou `Source *SourceResponse json:"source,omitempty"` —
  populado só nesta rota com a flag; `null`/omitido nos demais endpoints de artigo, mesmo padrão já
  usado pelo `is_read`.
- **Testes**: unit e integração cobrindo `with_sources=true` (source populado, todos os campos) e
  ausente/`false`/qualquer outro valor (`source` omitido/null, sem erro — a própria regra da
  convenção testada).

## Testes

`go vet ./...` limpo e suíte completa verde (`go test ./...`, 0 falhas) após a rodada completa de
ajustes (produção + ~20 arquivos de teste tocados pelo rename do sqlc e pelo campo `name`
obrigatório).

## Como testar

- **name em sources**: `POST /v1/sources/create` sem `name` → 400; com `name` de 121+ caracteres →
  400; `name` válido → 201 com `name` no corpo. `PUT /v1/sources/:id` segue a mesma regra.
- **with_sources**: `task sdfull` (semeia fontes/feeds/artigos) e depois
  `GET /v1/feeds/{id}/articles?with_sources=true` — cada item vem com `source: {...}` preenchido.
  Sem o parâmetro (ou com qualquer valor diferente de `true`) o campo `source` não aparece.
