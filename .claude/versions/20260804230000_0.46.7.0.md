# 0.46.7.0 — Revisão: container rodava como root (0.41 / 0.42)

## Resumo

Sexta e **última** leva da revisão da 0.46. Escopo: **0.41** (split do compose, bind em loopback) e
**0.42** (multi-ambiente, CI/CD). É a única área do projeto que nenhum teste cobre, então tudo aqui
saiu de leitura e de verificação manual contra o comportamento real.

Fecha o escopo 0.38 → 0.45 aberto no início da 0.46.

## Achado — o container rodava como root

O `Dockerfile` não tinha diretiva `USER`. O estágio final é `alpine:3.21` com `CMD ["./api"]`, ou seja,
uid 0.

Nada ali precisa de root: a app escuta `API_PORT` (3000 por padrão, bem acima da faixa privilegiada),
não escreve nada em disco — todo estado vive no Postgres via `DATABASE_URL` — e o binário chega pronto
do estágio de build. Rodar como root só amplia o que um comprometimento da app, ou de uma das suas
dependências, alcançaria.

**Correção**: usuário `appuser` (uid 10001) criado no estágio final, binário copiado com
`--chown=appuser:appuser`, e `USER appuser` antes do `CMD`.

**Verificado na imagem real**, não só por leitura:

```
uid=10001(appuser) gid=10001(appuser) groups=10001(appuser)
-rwxr-xr-x    1 appuser  appuser  /app/api
```

E o binário sobe: falha em `DATABASE_URL must be set`, que é o erro esperado sem banco — não em
permissão.

## Comentário que apontava para um arquivo inexistente

`docker-compose.yaml` e `docker-compose.staging.yaml` instruíam a usar `docker-compose.prod.yaml`. O
arquivo é `docker-compose.production.yaml`. O `Taskfile` sempre esteve certo, então `task prod-up`
nunca quebrou — mas quem seguisse o comentário para montar o comando à mão receberia "no such file",
justamente num arquivo cujo propósito é dizer ao operador qual overlay aplicar. Corrigido nos dois.

Também documentei que o `EXPOSE 3000` do Dockerfile é **apenas metadado**: ele não publica nada e não
consegue ler `API_PORT` em runtime. Quem muda a porta de verdade é a variável, que o compose publica e
o healthcheck lê.

## Verificado e sem ressalva

Esta leva foi a que mais confirmou o que estava documentado — vale registrar, porque o padrão das
levas anteriores foi o contrário:

- **Deploy é mesmo inerte.** `if: ${{ vars.DEPLOY_ENABLED == 'true' }}` no job, e só dispara nos
  branches `staging`/`production`. A afirmação se sustenta.
- **Portas todas em loopback.** `api` (base), `postgres` e `pgadmin` (override) publicam com prefixo
  `127.0.0.1:`. Staging e produção não publicam porta de banco nenhuma.
- **pgAdmin não existe fora de dev**, por ausência: ele mora só no `docker-compose.override.yaml`, e o
  `-f` explícito de staging/produção desliga o auto-merge do override. Produção não depende de alguém
  lembrar de removê-lo.
- **Segredos.** O `.gitignore` cobre `.env` e `.env.*` liberando só `.env.example` e `.env.*.example`;
  os arquivos de exemplo trazem apenas `CHANGE_ME`, nunca um valor real.
- **O `--env-file` está no lugar certo.** Interpolação de `${API_IMAGE}` no compose vem do
  `--env-file`, não do `env_file:` do serviço (que só popula o ambiente **dentro** do container). O
  `Taskfile` passa `--env-file` em `staging-up` e `prod-up`, então a distinção está correta.
- **CI não cai na armadilha do `gofmt`.** O passo captura a saída de `gofmt -l` numa variável e sai com
  1 se houver conteúdo, em vez de confiar no exit code (que é 0 mesmo com arquivos desformatados).

## Observação sem ação

O binário final tem ~154 MB, o que é grande para um binário Go mesmo com `-trimpath -ldflags="-s -w"`.
Não investiguei a fundo e **não** o classifico como defeito — só registro, porque tamanho de imagem
afeta tempo de deploy e custo de ECR. Vale uma análise própria se o deploy ficar lento.

## Como testar

```bash
task test-all
```

Para conferir o usuário do container:

```bash
docker build -t news-feed-api:check . && docker run --rm --entrypoint id news-feed-api:check
```

roadmap é a **0.47.0.0** (migração Fiber v2 → v3), e ficou proposta uma **0.48** para a auditoria de
