# Versão 0.32.0.0 — poll de feeds com não lidas + skip da LLM no tratamento

**Data:** 2026-07-09

Duas features independentes do roadmap 0.32, entregues juntas nesta versão.

## 1. `GET /v1/feeds/check-for-new-articles`

Rota leve de **polling** que responde quais feeds ativos do usuário do token possuem notícias não
lidas, e quantas. Pensada para o client consultar de tempos em tempos; no futuro pode virar SSE/WebSocket.

### Desenho e decisões

- **Resposta**: objeto JSON plano `{ "<feed_id>": <int_não_lidas>, ... }`, conforme o roadmap. Só
  aparecem feeds com **≥1 não lida**; quando não há nenhuma, a resposta é `{}`.
- **Sem paginação**: é um **indicador**, não uma listagem de registros (o `PROJECT.md` abre exceção
  para métricas/indicadores; o usuário tem no máx. 5 feeds). Confirmado com o Nathan.
- **Contagem em SQL** (respeita a convenção anti-filtragem-em-Go): nova query
  `CountUnreadArticlesByFeedForUser` (`sqlc/queries/articles_feeds.sql`) — junta `feeds` + `articles_feeds`
  + `articles` exigindo **ambos os lados ativos** (regra de validade da junction), filtra `is_read=0`
  e agrupa por feed. Os inner joins + o filtro fazem feeds sem não lidas simplesmente não aparecerem.
- **Rota estática antes de `/:id`**: registrada antes das rotas com param para nunca ser capturada como
  um id (o Fiber já prioriza estática sobre param, mas a ordem explícita segue o precedente de
  `sources/rss-discovery`).
- **Escopo por usuário**: tudo passa pelo `user_id` do JWT; feeds de outros usuários nunca entram na conta.

### Arquivos

- `sqlc/queries/articles_feeds.sql` — query nova (+ regeneração do sqlc).
- `services/controllers/articles_feeds.go` + `interfaces.go` — método `CountUnreadByFeedForUser`.
- `services/endpoints/v1/feeds/check_new_articles.go` — handler `CheckForNewArticles`.
- `main.go` — registro da rota.

### ⚠️ Bug de build encontrado e contornado (sqlc + UTF-8)

Durante o desenvolvimento, o `sqlc generate` estava **truncando o final do SQL gerado** (ex.:
`GROUP BY f.id` virava `GROUP BY f.`), gerando SQL inválido e 500 em runtime. Causa raiz: um
**travessão `—` (em dash, U+2014, 3 bytes UTF-8)** no comentário `-- ...` da query. O sqlc conta
**bytes como se fossem runes** ao recortar o texto, então cada caractere multibyte no comentário
desloca o offset e corta o rabo do SQL. **Correção**: manter os comentários das queries `.sql`
**100% ASCII** (troquei o `—` por `-` e deixei um aviso no próprio comentário). Fica registrado como
armadilha do projeto.

## 2. Skip da LLM no tratamento via `TREATMENT_AI_ACTIVE`

Implementa o comportamento já documentado em `PROJECT.md` ("Revisando o conteúdo"): quando
`TREATMENT_AI_ACTIVE=false`, o passo de **revisão do texto pela LLM** é pulado e o **conteúdo original
do RSS segue adiante**.

### Desenho e decisões

- Implementado como um **decorator passthrough** na mesma cadeia que já existia
  (`ai.NewPassthroughTreater()`), consistente com `sanitize`/`verbose`. Nada de `if` espalhado no
  pipeline (`discovery.processOne` continua sem saber disso).
- **A sanitização (bluemonday) continua sempre rodando** sobre o conteúdo que segue. Ou seja, o flag
  desliga **só** a revisão por IA — não a sanitização. Isso evita que HTML cru do RSS (`<script>`,
  links, etc.) entre no banco. Decisão fechada com o Nathan (a alternativa "cru total" abriria XSS
  armazenado).
- **Escopo do flag**: afeta **apenas** o passo da LLM (o `treater`). Detecção de idioma (lingua-go),
  nomeação de keywords (`KEYWORDS_MODE`) e julgamento seguem inalterados.
- O **endpoint dry-run** `POST /v1/articles/treatment` reusa o mesmo `treater` montado no `main.go`,
  então **honra automaticamente** o `TREATMENT_AI_ACTIVE` (sem toggle por request).

### Arquivos

- `services/ai/passthrough.go` — `NewPassthroughTreater` (+ `passthrough_test.go`).
- `main.go` — a montagem do `treater` escolhe `buildProvider(...)` (flag ligado) ou o passthrough
  (flag desligado), sempre embrulhado por `sanitize` e `verbose`. `.env.example` já tinha
  `TREATMENT_AI_ACTIVE=true`.

## Como testar manualmente

1. `ENVIRONMENT=development task ls` (ou `go run main.go`), `task sdfull` para semear e pegar um token.
2. **Poll**: `GET /v1/feeds/check-for-new-articles` com o Bearer → objeto `{ feed_id: n }`. Marque uma
   notícia como lida (`PUT /v1/articles/{id}/read`) e repita — a contagem cai / o feed some. Requisição
   pronta no Bruno: `feeds/check-for-new-articles`.
3. **Skip da LLM**: rode com `TREATMENT_AI_ACTIVE=false` e chame `POST /v1/articles/treatment` — o
   `content` de resposta é o original (apenas sanitizado), sem chamada à LLM (e sem consumir quota).
   Com `TREATMENT_AI_ACTIVE=true`, o conteúdo volta revisado pela LLM.
