# 0.47.0.0 — Migração Fiber v2 → v3

## Resumo

Sai o `gofiber/fiber/v2 v2.52.14`, entra o `v3.4.0`. Era a única dependência do projeto uma major
inteira atrás, e o v2 entra em manutenção com o v3 estável. Sem CVE aberto — era dívida, não incêndio.

Contrato da API **inalterado**: o client não precisa de nada. Suíte completa verde (22 pacotes, zero
falhas) e boot real verificado.

## O que a estimativa acertou

O levantamento da 0.46 (feito contra o **fonte** do v3.4.0, não contra a documentação) previu ~58
pontos, e esses se confirmaram:

- 47 assinaturas `*fiber.Ctx` → `fiber.Ctx` (o `Ctx` virou interface) e 83 imports.
- 3 `c.Redirect(url, status)` → `c.Redirect().Status(s).To(url)`, todos no fluxo de login OAuth.
- 1 config de cors (`AllowOrigins`/`AllowMethods`/`AllowHeaders`: string → `[]string`).
- 2 `app.Test(req, 5000)` → `fiber.TestConfig{Timeout: ...}`.

E o principal: **os 90 `c.Context()` passaram intactos**, como previsto. A doc oficial afirma que
`Context()` foi removido; não foi — houve troca de cadeiras. O `Context()` do v2 (que devolvia
`*fasthttp.RequestCtx`) virou `RequestCtx()`, e o nome `Context()` passou a devolver um
`context.Context` de verdade, absorvendo o papel do `UserContext()`, que sumiu.

Não bastou compilar: auditei a **forma de uso** dos 90. Todos são "passa adiante como primeiro
argumento" (`runTx(c.Context(), ...)` e afins), e **nenhum** faz `c.Context().<algo>`, que indicaria
dependência do fasthttp e exigiria `RequestCtx()`.

## A cauda que a estimativa não cobriu

Registrada porque eu havia declarado confiança "alta no volume, moderada na cauda" — e a cauda apareceu:

- **`DisableStartupMessage` saiu do `fiber.Config`** (migrou para `ListenConfig`). 32 ocorrências,
  todas em testes; o `main.go` não usava. Como testes nunca chamam `Listen`, bastou remover.
- **Registro de rota mudou de assinatura**: v2 era `Get(path, handlers ...Handler)`, v3 é
  `Get(path, handler any, handlers ...any)`. 31 rotas no `main.go`, 94 nos testes.
- **`BodyParser` → `Bind().Body()`**: 12 sites.
- 11 arquivos de teste declaravam uma interface inline espelhando a assinatura antiga de `Test`.

## O ponto perigoso, e o erro que cometi nele

A assinatura nova de rota é a armadilha da migração. Os nomes (`handler`, depois `handlers`) sugerem
precedência, mas o fonte mostra que `Add` faz `append([]any{handler}, handlers...)` e registra **na
ordem** — é uma cadeia ordenada, e o primeiro elemento roda primeiro. Se alguém assumir o contrário e
inverter, **a autenticação roda depois do handler**, compilando normalmente.

Como Go não consegue espalhar uma slice em `(primeiro, resto...)`, a adaptação foi centralizada em dois
helpers com essa explicação escrita: `addRoute` no `main.go` e `testutils.AddRoute` para os testes.

**Erro cometido e registrado**: a primeira transformação usou regex com `DOTALL`, que atravessou
fronteiras de linha e danificou 6 rotas. O compilador pegou 3 (handler único dentro de `addRoute`); os
outros 3 passavam uma **slice como handler único** — o que compila, porque o parâmetro é `any`, e
explodiria só no boot. Depois de corrigir, escrevi uma auditoria que verifica as 36 rotas por forma
(toda cadeia via helper, toda chamada direta com handler único) em vez de confiar no build. A segunda
transformação, nos testes, foi ancorada por linha.

## Verificação

Além da suíte (22 pacotes, zero falhas — inclusive os testes de 401 e de 403, que é o que pegaria a
inversão de ordem), fiz um **boot real** numa porta livre, porque `app.Test` não passa pelo listener:

```
Fiber v3.4.0 — Server started on http://127.0.0.1:3999 — Total handlers: 159

GET /v1/health          -> 200   (rota pública, handler único)
GET /v1/articles        -> 401   (autenticação roda ANTES do handler)
GET /v1/sources         -> 401
POST /v1/sources/create -> 401   (nunca 200 nem 500)
```

## Melhoria aproveitada no cors

A conversão de string para `[]string` moveu o split para o nosso lado, e a guarda passou a ser sobre a
**lista já parseada**, não sobre a variável crua. Isso fecha uma brecha que o código v2 tinha: um
`CORS_ALLOWED_ORIGINS` valendo `","` ou `"  "` é não-vazio como string mas não libera origem alguma, e
entregar isso ao middleware é exatamente o caso que poderia cair no fallback `"*"`.

## Achados fora do escopo, corrigidos

- **`PROJECT_VERSION` estava em `0.44.0.0`** nos três `.env.*.example`, três versões atrás. O
  `/health` publica esse valor, então a API anunciava versão errada. Atualizado para `0.47.0.0`.
  **O `.env` local de cada máquina precisa ser atualizado à mão** — foi ali que eu notei, com o boot
  respondendo `"version":"0.44.0.0"`.
- **`services/safehttp` não havia sido registrado no `structure.md`** na 0.46.6. Falha minha contra uma
  regra explícita do projeto; corrigido aqui.

## Ficou proposto, não feito

**Injetar a versão em build time** (`-ldflags -X`) em vez de manter `PROJECT_VERSION` em quatro
arquivos de env. Sincronização manual em quatro lugares é o motivo de ter derivado três versões, e vai
derivar de novo. É mudança no Dockerfile e no CI, então merece decisão à parte.

**Rotas idiomáticas do v3**: dentro de cada grupo (`/sources`, `/articles`, `/feeds`), todas as rotas
exigem autenticação, então o v3 favoreceria `group.Use(authMiddleware...)` + `group.Get(path, handler)`,
dispensando os helpers de cadeia. Deliberadamente **não** feito: seria redesenho de wiring dentro de uma
migração, e o comentário atual do `main.go` justifica a escolha per-route. Vale avaliar depois.
