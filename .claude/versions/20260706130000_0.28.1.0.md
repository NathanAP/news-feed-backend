# Versão 0.28.1.0 — patch da revisão da 0.28 (banco sob concorrência + erro tipado de UNIQUE)

**Data:** 2026-07-06

Fase 2 da 0.28: a **revisão** (Opus 4.8, foco no acumulado desde a última revisão formal — 0.17 —
priorizando a concorrência da 0.27). A revisão produziu dois achados; ambos corrigidos neste patch.
Pelas regras (`Bugs graves devem ter preferência e podem garantir uma versão única de patch`), a
correção subiu uma versão de patch dedicada.

## Achado 1 (grave) — banco de produção sem `busy_timeout`, incompatível com o paralelismo da 0.27

### Diagnóstico
`main.go` abria o SQLite com `sql.Open("sqlite", "./db/news_feed.db")` — **sem** PRAGMA e **sem**
config de pool. O SQLite permite um único writer por vez; sem `busy_timeout`, o segundo writer que
encontra o banco travado **falha na hora** com `SQLITE_BUSY` ("database is locked") em vez de esperar.
O pool do `database/sql` é ilimitado por padrão, então múltiplas conexões escrevem em paralelo.

A 0.27 introduziu exatamente esse cenário: com `DISCOVERY_CONCURRENCY > 1`, os goroutines de
`discovery.processOne` chamam `persist`/`judge` (cada um abre sua transação via `WithTransaction`)
concorrentemente → colisão de escrita → `SQLITE_BUSY`. Como `WithTransaction` não tem retry e o erro
é logado-e-engolido em `processOne`, o resultado era **artigo descartado** justo sob a concorrência
que a feature existe para habilitar. Pior: mesmo com `DISCOVERY_CONCURRENCY=1`, a cron roda num
goroutine próprio enquanto o Fiber atende requisições — uma escrita da cron sobreposta a uma escrita
de API já podia dar `SQLITE_BUSY`. Ou seja, era um risco latente que a 0.27 amplificou.

Inconsistência que confirmou o achado (o PRAGMA já era conhecido, só faltou na produção):
- `cmd/seed/seed.go` abre com `?_pragma=busy_timeout(5000)`.
- `tests/utils/db.go` usa `SetMaxOpenConns(1)` (serializa tudo numa conexão → esconde o bug nos testes).
- `main.go` não tinha nenhum dos dois.

### Correção
O DSN de produção passou a carregar os PRAGMAs (mesma sintaxe `_pragma=` do modernc já usada no seed):

```
./db/news_feed.db?_pragma=busy_timeout(5000)&_pragma=journal_mode(WAL)
```

- `busy_timeout(5000)`: o writer espera até 5s pelo lock em vez de falhar imediatamente.
- `journal_mode(WAL)`: leitores não bloqueiam o writer, então leituras de API prosseguem durante a
  varredura de descoberta.

São parâmetros de connection string **específicos do SQLite**, aplicados num único ponto (`main.go`),
sem tocar controllers, queries, schema ou lógica de domínio. Numa futura troca para Postgres eles
simplesmente desaparecem junto com o `sql.Open("sqlite", ...)` — não geram dívida para a migração.

## Achado 2 (robustez) — detecção de violação de UNIQUE por substring

### Diagnóstico
Cinco call sites (`users.go`, `sources.go`×2, `articles.go`×2) detectavam violação de UNIQUE com
`strings.Contains(err.Error(), "UNIQUE constraint failed")` — frágil (depende do texto do erro do
driver). Havia ainda um acoplamento com o Achado 1: sem `busy_timeout`, o insert perdedor de um batch
concorrente tende a receber `SQLITE_BUSY` (não mapeado) em vez de um UNIQUE limpo, então a "dedup
concorrente segura" descrita na 0.27 só se sustenta de verdade **após** o Achado 1.

### Correção
Novo helper em `services/controllers/sqlite_errors.go`:

```go
func isUniqueViolation(err error) bool {
    var serr *sqlitedriver.Error
    return errors.As(err, &serr) && serr.Code() == sqliteConstraintUnique // SQLITE_CONSTRAINT_UNIQUE = 2067
}
```

O `modernc.org/sqlite` liga extended result codes no open da conexão (`conn.go`), então uma violação
de UNIQUE sempre chega com `Code() == 2067`. Aplicado nos 5 call sites; imports de `strings` agora
sem uso removidos de `users.go` e `sources.go` (mantido em `articles.go`, que usa `strings` no
`encodeKeywords`).

## Testes

- `go vet ./...`, `go build ./...` e a suíte completa (`go test ./...`) — todos verdes.
- Os testes de "já existe" (sources/articles/users → 409/`*AlreadyExists`) exercitam o novo
  `isUniqueViolation` contra o driver modernc real (in-memory), validando a detecção tipada.
- O caminho de concorrência da 0.27 continua coberto pelos testes de `integration/discovery` e
  `integration/cron` (que rodam com `SetMaxOpenConns(1)`); a correção do banco é de configuração de
  DSN de produção, fora do alcance do banco de teste in-memory.

## Como testar

- **Banco sob concorrência (manual/homologação):** `DISCOVERY_CONCURRENCY=4`, CRON ativa e várias
  sources → antes, logs de `persist failed ... database is locked` e artigos sumindo; agora, as
  escritas serializam via `busy_timeout` sem erro. O arquivo do banco passa a ter `-wal`/`-shm`.
- **UNIQUE tipado:** criar uma source/article/usuário duplicado → `409` com o erro de "já existe"
  (comportamento idêntico ao anterior, agora por código de resultado do driver).

## Observações

- `busy_timeout` fixo em 5s (espelha o seed). Se um dia a contenção exigir, dá para expor via env.
- O teto real de escrita concorrente do SQLite permanece (single-writer). Para escrita concorrente de
  verdade + múltiplas réplicas, o caminho segue sendo Postgres (ver ROADMAP "Escalabilidade futura");
  este patch deixa o SQLite seguro e sem dívida até lá.
