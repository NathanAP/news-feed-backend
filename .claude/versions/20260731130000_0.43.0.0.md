# 0.43.0.0 — Barrar usuários inativos na descoberta

## Resumo

A CRON julgava toda notícia descoberta contra os feeds de **todos** os usuários, inclusive os que
abandonaram o app. Isso gastava IA à toa e mantinha feeds mortos "recebendo" notícias que ninguém iria
ler. A 0.43 introduz um sinal de atividade (`last_active_at`) e um filtro na camada 1 do julgamento que
pula feeds de usuários inativos.

## O sinal: `last_active_at`, não `last_login_at`

O ponto sutil (levantado no planejamento): o `last_login_at` existente **não** significa atividade —
ele só é escrito no login completo do Google, que acontece no máximo a cada janela do refresh token
(~30 dias). Um usuário que loga uma vez e usa o app diariamente via refresh ficaria com `last_login_at`
de até 30 dias atrás, e seria marcado como inativo por engano.

Por isso, coluna nova:

- **`users.last_active_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP`** (migração
  `20260731120000`). O `ADD COLUMN` com default preenche toda linha existente com a hora da migração —
  backfill automático, ninguém congela no deploy. Usuário novo nasce com `now()` (acabou de logar).
- **Escrito no `/auth/refresh`** (o batimento ~horário do app), **no login** e **no `dev-login`**.
  Query `UpdateUserLastActive`, método homônimo no `UserController`, chamado dentro da transação em cada
  um desses fluxos.
- **Não vai no `access_token`**: muda toda hora, seria churn puro; é campo só de banco.

## O filtro: predicado na camada 1

`FindCandidateFeedsByKeywords` (a query de overlap de keywords) ganhou um `JOIN users` com o predicado
de atividade **na mesma instrução SQL** — não é uma passada separada, é uma condição a mais:

```sql
JOIN users u ON u.id = f.user_id
  AND u.status = TRUE AND u.removed_at IS NULL
  AND (sqlc.arg(inactive_days)::int = -1
       OR u.last_active_at > CURRENT_TIMESTAMP - make_interval(days => sqlc.arg(inactive_days)::int))
```

Assim feeds de inativos nem chegam a ser candidatos → a economia de IA acontece na camada 1, antes da
camada 2. `inactive_days = -1` desliga o filtro (todo mundo conta como ativo).

O valor vem da env `DAYS_UNTIL_USER_IS_INACTIVE` (`-1` desliga, `0` é rejeitado pois congelaria todo
feed, default 15), parseada no `main.go` e passada por parâmetro até os dois lugares que chamam a query:
o processor da CRON (`TreatmentProcessor`) e o dry-run de julgamento (`JudgeArticle`).

## Trade-off aceito

O julgamento não é retroativo, então um usuário que volta **perdeu** as notícias descobertas enquanto
estava inativo — o feed dele fica com um buraco naquele período. É decisão consciente (documentada no
`PROJECT.md`, seção Usuário e "Busca por usuários aptos"), e só afeta quem realmente abandonou o app
por mais que a janela.

## Testes

- **Filtro (integração contra o Postgres)**: dois usuários com feed idêntico, um ativo e um com
  `last_active_at` recuado 40 dias — só o ativo vira candidato; recuado 5 dias (< janela) continua
  vindo; `-1` traz os dois. (`tests/integration/api/feeds/candidate_filter_test.go`)
- **Escrita (o elo crítico)**: um `/auth/refresh` real carimba `last_active_at` de volta para ~agora,
  mesmo partindo de um usuário recuado 40 dias. Sem esse write, o filtro se auto-sabotaria (todo mundo
  viraria inativo). (`tests/integration/api/auth/last_active_test.go`)
- Os call sites existentes de `FindCandidatesByKeywords`/`NewTreatmentProcessor`/`JudgeArticle` passaram
  a receber `inactiveDays`; nos testes que não exercem o filtro, passa-se `-1` (comportamento inalterado).

## Como testar manualmente

Com o banco semeado (`task sdfull`) e a CRON ligada, o usuário dev nasce ativo (`last_active_at = now()`)
e o `dev-login` o mantém ativo, então a descoberta associa normalmente. Para ver o filtro agir:

1. No pgAdmin4: `UPDATE users SET last_active_at = now() - interval '40 days' WHERE email = '<dev>';`
2. Force uma descoberta (`GET /v1/sources/{id}/article-discovery` é dry-run; a CRON real associa) — os
   feeds do usuário recuado deixam de receber.
3. `DAYS_UNTIL_USER_IS_INACTIVE=-1` no `.env` desliga o filtro (útil em dev para não ter surpresa com um
   banco parado).
