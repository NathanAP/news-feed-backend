# 0.44.0.0 — Robustez do scheduler da CRON

## Contexto

A versão nasceu como "entender como a CRON pode ser organizada" (duas perguntas: precisa de uma CRON por
worker? e se demorar demais?). A análise respondeu as duas e, no caminho, achou dois furos de robustez
concretos no `NewScheduler` — que usava `robfigcron.New()` **sem nenhum wrapper**.

## As respostas da análise

- **Uma CRON por worker?** Não. A CRON é o gatilho/produtor (um tick = uma varredura); workers são
  consumidores (hoje o pool de goroutines `DISCOVERY_CONCURRENCY`; amanhã, réplicas de container). Uma
  CRON por worker duplicaria a varredura inteira → descoberta e IA duplicadas. Ao escalar, o alvo é
  **uma varredura só**: scheduler dedicado (uma réplica com `RSS_FEED_CRON_ACTIVE=true`) agora; advisory
  lock do Postgres se um dia quiser réplicas idênticas sem "uma especial". A fila distribuída
  (arquivada no ROADMAP) é a resposta de escala grande, não pra agora.
- **E se demorar demais?** Toda chamada externa já é limitada (RSS 30s no HTTP client, Gemini 60s,
  Ollama/Groq 120s), então um sweep é longo mas **finito** — ele sempre termina. Um timeout por sweep,
  com valor fixo, só arriscaria cortar um sweep legítimo em progresso, então foi **descartado**.

## As correções (o que faltava no scheduler)

`NewScheduler` passou a envolver cada tick com dois `JobWrapper` da robfig/cron:

- **`SkipIfStillRunning`** — se um sweep passar do intervalo (`@every 15m`), o próximo tick é **pulado**
  em vez de iniciar um segundo sweep concorrente. Importante: **não é correção de integridade**. Dois
  sweeps sobrepostos não duplicam notícia — o índice único parcial `idx_articles_url_original_active`
  faz o Postgres serializar os inserts (um vence, o outro leva violação de unicidade → descartado
  graciosamente antes de julgar). É **economia de IA**: sem o guard, os dois sweeps gastariam a chamada
  de nomeação de keywords para os mesmos artigos.
- **`Recover`** — um panic dentro de uma varredura vira log (via um `cronLogger` que roteia pro logger
  do app) em vez de derrubar o processo. A CRON é **in-process**, então sem isso um único sweep ruim
  (um RSS malformado, um nil deref) levaria a API inteira junto — o que a regra do projeto proíbe
  ("exceções não devem derrubar a aplicação"). O `recover.New()` do Fiber (adotado na 0.37.3) só cobre
  handlers HTTP, nunca essa goroutine. É o paralelo dele pra CRON.

## Sobre testes

Deliberadamente **sem teste novo**. Os dois são wrappers da própria robfig/cron (biblioteca
estabelecida); um teste significativo ou testaria a biblioteca, ou seria um teste de timing frágil
(subir o scheduler com `@every 1s` + sleep e torcer). É o mesmo tratamento que a 0.37.3 deu ao
`recover.New()` do Fiber — adotado sem teste custom por ser comportamento de biblioteca confiável. O
build, o `vet` e a suíte inteira seguem verdes.

## Nota de escala (não implementada, só registrada)

Com volume grande (ex.: ~1000 fontes), o teto real nunca é o Go — é o **rate limit do provedor de IA**
(~2 chamadas por notícia). Aí um backlog é inevitável se a entrada superar a vazão da IA; a resposta é a
**fila persistente + workers** (arquivada). Antes dela, as alavancas baratas: `KEYWORDS_MODE=local`
(tira a nomeação de keywords do rate limit do provedor), os filtros que já cortam IA (triagem do
julgamento + inativos da 0.43), e conditional GET no RSS (pular feed que não mudou). O `SkipIfStillRunning`
segura até lá, mas é válvula de segurança, não solução de escala.
