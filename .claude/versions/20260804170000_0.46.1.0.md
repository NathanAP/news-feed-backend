# 0.46.1.0 — Revisão: primeira leva (0.45, outboundlinks)

## Resumo

Primeiro lote da metade "Revisão" da 0.46. Escopo desta leva: a **0.45** (`article_outbound_links` +
`services/outboundlinks`), escolhida como primeira por risco — é a versão mais recente, a mais
complexa, e está no caminho de leitura de **toda** notícia servida.

Patch conforme a regra "alterações causadas pelo revisor sobem uma versão de patch".

Verificado e **sem ressalva**: o batch de leitura não tem N+1 (uma query por página, `byID` único
resolvendo todos os artigos, em `list.go`, `get.go`, `articles.go` e `translate.go`), e a invariante
central da 0.45 — id e token `{CLIENT_URL}` nunca passam pelo bluemonday — se mantém em todos os call
sites.

## Achado 1 — `toStored` casava domínio sósia (bug dormente)

`services/outboundlinks/outboundlinks.go` usava `strings.HasPrefix(href, clientURL)` sem exigir que o
prefixo terminasse numa fronteira de URL. Comprovado com sonda antes de corrigir:

```
CLIENT_URL = https://news.example.com
href       = https://news.example.com.evil.com/x
stored     = "{CLIENT_URL}.evil.com/x"      <- gravado como se fosse link interno
```

**Por que passou despercebido**: enquanto o `CLIENT_URL` não muda, o `expand` devolve exatamente a
string original e o round-trip fecha. O dano só aparece no dia da troca de domínio, quando um link
**externo** passa a seguir a mudança do **nosso** domínio (`https://novo.com.evil.com/x`).

**Por que não é caso rebuscado**: basta o `CLIENT_URL` ser `https://algo.com` e uma notícia linkar
`https://algo.com.br/...`. Num agregador de notícias brasileiro, `.com.br` ao lado de `.com` é rotina.

Correção: `toStored` só tokeniza se o que vem depois do prefixo for vazio ou começar com `/`, `?` ou
`#` (helper `isURLBoundary`). Três testes novos: hosts sósia ficam literais, as formas legítimas
(origin nu, `/`, path, query, fragment) continuam tokenizadas, e um round-trip provando que o link
externo **não** acompanha a mudança de `CLIENT_URL`.

## Achado 2 — o "pre-remove cleanup" documentado não existia

O comentário de `RetargetArticleOutboundLinksByHref` (e o version file da 0.45) afirmavam **dois**
callers. Existia **um**: o retro-link em `processor.go:343`. O `DELETE /v1/articles/{id}` só chamava
`SoftDelete`.

**Consequência**: ao remover a notícia L, as linhas apontando para `{CLIENT_URL}/articles/{L.id}`
permaneciam. Leitores de notícias antigas recebiam link para uma página que responde 404 — leituras
excluem removidas. O fallback projetado (repontar para `L.url_original`) nunca foi ligado.

Documentação que descreve comportamento inexistente é pior que ausência de documentação: quem lê
acredita que está coberto.

Correção (opção (a), decidida junto): `DeleteArticle` recebe o `ArticleOutboundLinkControllerInterface`
e chama `Retarget(InternalHref(id), article.UrlOriginal)` **dentro da mesma transação** e **antes** do
soft delete, para que uma falha faça rollback do conjunto. Wiring atualizado no `main.go` e nos três
setups de teste (unit, integração, e2e).

Dois testes de integração novos: o retarget acontece; e ele **não** toca links não relacionados (o
match é por href exato, então link externo e link interno para outra notícia ficam intactos).

**Regressão comprovada**: desligando a correção, o teste falha com
`actual: "{CLIENT_URL}/articles/019fce88-..."` em vez da `url_original`.

## Achado 3 — `sqlc.yaml` subestimava a própria rota de saída

O comentário prometia que migrar para pgx nativo seria "this one line plus a regen". Não é: o regen
troca `sql.NullString`/`sql.NullTime` por `pgtype.*` em todo model, controller, mock e teste que
encoste num campo nulável. Comentário reescrito, registrando que é versão própria — e que o prêmio,
se um dia for feito, é o `lib/pq` (hoje no `go.mod` só como encoder do `pq.Array`) cair fora de graça.

## Achado 4 — a suíte e2e é instável sob carga (observado, NÃO corrigido)

Num dos `task test-all` desta versão, **10 testes e2e** (`api/articles` e `api/feeds`) falharam de uma
vez. Não reproduziu: os dois pacotes passam isolados, e o run completo seguinte passou com zero falhas.
Os pacotes de **integração** de articles — que exercitam exatamente o código alterado nesta versão —
passaram nos dois runs, então não é regressão desta leva.

A causa provável é contenção: o `go test` roda cada pacote num processo separado e em paralelo, e as
camadas de integração/e2e sobem containers. Com Docker em ~7,9 GB, vários pacotes disputando ao mesmo
tempo é o suficiente.

**Por que isso não é só chateação local**: o `ci.yml` roda `go test ./...` em `ubuntu-latest`, que tem
2 vCPU e ~7 GB — mesma ordem de grandeza. Um flake assim reprova PR sem motivo, e o preço real de um
teste instável é que as pessoas aprendem a ignorar vermelho.

Não corrigido de propósito: a correção provável (limitar o paralelismo de pacotes com `-p`, no Taskfile
e no CI) troca tempo de suíte por estabilidade, e essa é uma escolha a fazer junto. Fica como primeiro
item candidato da próxima leva de revisão.

## Como testar

```bash
task test-all
```

Os dois comportamentos corrigidos podem ser vistos isoladamente:

```bash
go test ./services/outboundlinks/ -run "LookAlike" -v -count=1
```

```bash
go test ./tests/integration/api/articles/ -run "TestIntegration_DeleteArticle" -v -count=1
```
