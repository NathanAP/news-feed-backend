# 0.42.0.0 — Preparação de staging/produção (compose multi-ambiente + CI/CD)

## Resumo

Deixa a estrutura de staging e produção pronta **sem depender de AWS** ainda: compose por ambiente,
alvos no Taskfile, templates de env e os workflows do GitHub Actions. Nenhum acesso à nuvem é necessário
pra isso existir — o CI roda de imediato, o deploy fica inerte até ser ligado. Alvo escolhido:
**EC2 + docker compose**. Postgres de produção (RDS vs container): **decisão adiada** de propósito.

## A correção de modelo que orienta tudo

O fluxo que estava no `PROJECT.md` (derrubar → `git stash` → `git pull` → apagar `.claude/`, `bruno/`,
`cmd/`, `test/` → subir) mira na camada errada:

- Constrói no servidor (toolchain no host, build não-reproduzível, meio-do-caminho quebrado).
- `git stash` no servidor = estado não reproduzível a partir do git.
- Apagar arquivos de dev é quase teatro: a imagem de produção (multi-stage) já é **só o binário** — sem
  `.claude`, `bruno`, `cmd`, `tests` nem fonte —, o `.dockerignore` já barra o resto do contexto, e as
  rotas de dev (`dev-login`, `treatment`, `judgement`) são barradas por `ENVIRONMENT` em runtime.

**Modelo adotado:** o CI constrói a imagem **uma vez**, empurra pro ECR, e o servidor só dá `pull` da
tag e sobe. Servidor nunca vê código. Deploy reproduzível, rollback = apontar pra uma tag anterior.

## O que mudou

### Compose multi-ambiente

- O `postgres` **saiu da base** pra cada overlay. Motivo técnico: o Compose adiciona/altera serviço num
  override mas **não remove** um serviço da base — então, com o postgres na base, produção com RDS seria
  obrigada a subir um container de banco inútil. Com o postgres por ambiente, cada um conta sua própria
  história de banco.
- **`docker-compose.yaml`** (base): só `api`, com `image: ${API_IMAGE:-news-feed-api:local}` e sem
  `env_file` (cada overlay nomeia o seu, pra produção nunca carregar um `.env` de dev por acidente).
- **`docker-compose.override.yaml`** (dev): `build: .`, `env_file: .env`, `DATABASE_URL` apontando pro
  serviço `postgres`, + `postgres` (container dev) + `pgadmin4`.
- **`docker-compose.staging.yaml`**: `api` (imagem, sem build) + `postgres` container (sem porta
  publicada). Banco descartável, staging barato e autocontido.
- **`docker-compose.production.yaml`**: `api` só. **RDS por padrão** (sem serviço postgres); um bloco de
  postgres container fica **comentado** pra quem quiser trocar. O nome do arquivo casa com o branch e o
  env file (`production` / `.env.production` / `docker-compose.production.yaml`), pro deploy selecionar o
  overlay com uma variável só.

### Taskfile

- `staging-up/down/logs` e `prod-up/down/logs`, com `-f` explícito (desliga o auto-override) e
  `--env-file` do ambiente.

### Templates de env

- `.env.staging.example` e `.env.production.example`: só os **nomes** das variáveis + defaults seguros,
  com os segredos marcados (`# secret`) e a orientação de virem de um secret store (SSM/Secrets Manager)
  em runtime, nunca do arquivo.
- `.gitignore`: acrescentado `!.env.*.example` — os templates são versionados; os `.env.staging` /
  `.env.production` reais (com segredo) continuam ignorados.

### CI/CD (GitHub Actions)

- **`ci.yml`** — sempre ativo. `gofmt -l`, `go vet ./...`, `go test ./...` (as camadas de
  integração/e2e sobem um Postgres descartável via testcontainers usando o Docker do runner). Não precisa
  de credencial nenhuma.
- **`deploy.yml`** — build → push ECR → deploy EC2 via SSH. Branch escolhe o ambiente
  (`staging`/`production`, mapeado a GitHub Environments). **Inerte** até a variável `DEPLOY_ENABLED=true`.
  Autenticação AWS por **OIDC** (role assumida, sem chave estática); secrets por Environment, nunca no
  YAML.
- **`.github/workflows/README.md`** documenta as variáveis/secrets necessárias e o que o host precisa ter.

### CRON de instância única

- O problema "vários workers + CRON" foi resolvido **por disciplina operacional**: produção roda uma
  instância só. A CRON é in-process (`RSS_FEED_CRON_ACTIVE`); uma segunda réplica rodaria a descoberta de
  novo (notícia e chamada de IA duplicadas). Documentado no compose de produção, nos templates de env e no
  README do CI. O fix de código (lock/fila distribuída) segue arquivado — só compensa com mais de uma
  réplica.

## Decisões adiadas (de propósito)

- **RDS vs container em produção**: o app só enxerga uma `DATABASE_URL`, então trocar é config, não
  rebuild. Produção usa RDS por padrão; o container fica comentado. Backup é tarefa da 0.43.
- **Workflow de deploy real**: existe e está documentado, mas só roda quando houver AWS e a flag ligada.

## Como testar (local, sem AWS)

```bash
# dev (auto-merge base + override)
docker compose config --services            # api, postgres, pgadmin4

# staging / produção (precisa de um .env.<amb>; copie do .example)
cp .env.staging.example .env.staging
docker compose --env-file .env.staging -f docker-compose.yaml -f docker-compose.staging.yaml config --services
cp .env.production.example .env.production
docker compose --env-file .env.production -f docker-compose.yaml -f docker-compose.production.yaml config --services   # só api
rm -f .env.staging .env.production
```

Os workflows são validados pelo GitHub ao subir (não há validador de Actions local). O `ci.yml` passa a
rodar sozinho no primeiro push/PR.
