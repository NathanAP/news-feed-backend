# 0.40.0.0 — Modo administrador

## Resumo

O `PROJECT.md` já descrevia o modo administrador por inteiro, incluindo uma lista de endpoints
exclusivos. Nada disso existia no código: não havia coluna, claim nem verificação. Esta versão faz o
código alcançar a documentação — e, no caminho, fecha três rotas que estavam abertas sem autenticação
nenhuma.

## O que mudou

### Banco

- Migração `20260729120000_users_admin_flag.sql`: `ALTER TABLE users ADD COLUMN admin BOOLEAN NOT NULL DEFAULT FALSE`.
    - `DEFAULT FALSE` é fail-closed: toda linha existente e todo usuário futuro nascem usuários comuns.
    - Sem índice, de propósito: a flag só é lida por chave primária (o middleware busca o requisitante
      por `id`), nunca filtrada. Um índice aqui seria peso morto — a mesma armadilha que o índice GIN
      da 0.37 caiu antes da 0.37.3 pegá-la.
- Query `SetUserAdmin` nova. Ela é separada em vez de virar um parâmetro do `CreateUser` por uma razão
  de segurança, não de estilo: mantendo a coluna fora daquele `INSERT`, o fluxo de login do Google fica
  **estruturalmente incapaz** de criar um administrador, mesmo que alguém erre um argumento no futuro.
  A promoção passa a ser sempre um ato explícito e separado.
- `schema.sql`: coluna acrescentada **no fim da tabela**, onde o `ALTER TABLE` a coloca de verdade. As
  queries usam `SELECT *` / `RETURNING *`, então a ordem declarada ali vira a ordem do `Scan` gerado —
  inserir a coluna no meio, onde lê melhor, quebraria o mapeamento. Ficou registrado em comentário.

### Autorização

- `middlewares/admin.go` novo:
    - `AdminResolver` concentra a resposta de "quem é administrador" para a aplicação inteira, sempre
      lendo `users.admin` no banco.
    - `RequireAdmin` roda depois do `authMiddleware` (ele responde "pode?", não "quem é?"). Não-admin
      recebe `403`; falha ao consultar a flag vira `500`, nunca `403` — é a mesma lição da 0.37.3, onde
      uma falha de banco virava 401 e deslogava todo mundo.
- `middlewares/app_status.go`: administradores atravessam a manutenção. A identificação só acontece
  no branch em que a aplicação **já está** desligada, então o caminho saudável continua pagando
  exatamente uma query, como antes. É fail-closed: token ausente/ruim, sessão encerrada ou erro de
  banco resultam em 503.
- `middlewares/auth.go`: `parseAccessToken` e `checkSession` extraídos das handlers para o guard de
  manutenção poder identificar o requisitante sem manter uma segunda cópia (que ia divergir) das regras
  de parsing e validação de sessão.

### Token e client

- `Claims.Admin` e `UserResponse.Admin`, preenchidos a partir de `user.Admin`.
- Ambos são **dica de client**, nunca fonte de autorização — a mesma separação já usada em
  `language_to_translate`. Se a decisão viesse do token, revogar o acesso de alguém só valeria quando o
  token expirasse (até uma hora), que é justamente quando esperar é inaceitável.
- `admin` é serializado sempre (sem `omitempty`): o client precisa distinguir "usuário comum" de
  "campo ausente".
- Nenhuma sessão precisou ser invalidada: um token emitido antes desta versão decodifica o campo
  ausente como `false`, que é a direção segura.
- Efeito colateral aceito e documentado: promover alguém vale na API na requisição seguinte, mas a UI
  de administrador do client só aparece quando o token for renovado. Como o claim só decide o que
  aparece na tela, o atraso é cosmético.

### Rotas

Guard aplicado nas 9 rotas que o `PROJECT.md` já listava, mais o `PUT /v1/system/app-status`.

## Problemas encontrados durante a execução

### Três rotas estavam abertas, sem autenticação nenhuma

- `DELETE /v1/auth/invalidate` e `DELETE /v1/auth/invalidate-all`: qualquer pessoa com a URL derrubava
  a sessão de qualquer usuário — ou de todos eles. Já constavam como "exclusivas de administrador" no
  `PROJECT.md`, mas não pediam nem token.
- `PUT /v1/system/app-status`: qualquer pessoa derrubava a aplicação inteira. Pior caso dos três,
  porque a rota é propositalmente isenta do guard de manutenção (para a app sempre poder ser religada).

### Deadlock do bypass de manutenção

O bypass identifica o administrador pelo `access_token`, que expira em
`JWT_ACCESS_TOKEN_EXPIRY_MINUTES`. Com `/auth/refresh` atrás do guard, um administrador cujo token
expirasse durante a manutenção receberia 503 justamente da chamada que o levaria de volta ao endpoint
que encerra a manutenção — e o `refresh_token` não carrega identidade que o bypass consiga ler. Ele
ficaria trancado do lado de fora, com a única saída sendo editar o banco na mão.

Solução: o grupo `/v1/auth` inteiro passou a ser registrado antes do guard. O custo é que um usuário
comum também consegue logar e renovar token durante a manutenção — inofensivo, já que todo o resto
responde 503 para ele.

### Ordem de middlewares e o slice compartilhado

`adminRoute` (e o `adminChain` equivalente nos testes) copia a cadeia de autenticação antes de
acrescentar. Guardar `append(authMiddleware, requireAdmin)` numa variável e reusá-la faria todas as
rotas compartilharem o mesmo array de fundo, e cada registro sobrescreveria o handler da rota anterior
— um bug silencioso em que as rotas acabariam todas apontando para o último handler registrado.

## Testes

- Fixtures: `NewTestAdminUser` (usuário distinto, com id/email próprios, para coexistir com o comum no
  mesmo banco) e `fixtures.CreateUser`, que persiste a flag — necessário porque a query de criação
  deliberadamente não a escreve, e sem isso um teste semearia um usuário comum acreditando ter semeado
  um administrador.
- Mock compartilhado `MockUserController` em `tests/mocks/services`: o middleware é montado em quatro
  grupos de rotas diferentes, e quatro cópias manuais da mesma interface seriam quatro lugares para
  esquecer quando ela mudar.
- `tests/utils/claims.go`: decodifica um token obtido num login real, para o E2E ler o `user_id` que
  precisa (e conferir o claim que o client vai usar).
- Unitários: 401/403/passa em cada rota admin, tabelados por rota para que uma rota nova sem guard
  apareça aqui. Mais o caso de falha de banco virando 500 e não 403.
- Integração: bypass de manutenção, administrador rebaixado bloqueado na requisição seguinte,
  administrador deslogado bloqueado, `/auth/refresh` respondendo durante a manutenção e o usuário comum
  que renova token mas continua levando 503.
- E2E: ciclo completo — login como usuário comum, recusa, promoção pelo banco, mesma ação aceita **sem
  novo login**, desligamento da aplicação, administrador trabalhando durante a manutenção, rebaixamento
  no meio dela e religamento.
- Testes que provam a decisão central: um token cujo claim diz `admin: true` mas cuja linha no banco
  diz o contrário recebe 403/503. Se a autorização um dia passar a confiar no claim, é o que quebra.

## Como testar

```bash
task ta
```

Manualmente, com a app no ar e o banco semeado (`task sdfull` — o usuário dev já é administrador):

1. `POST /v1/users/dev-login` e confira `admin: true` em `GET /v1/users/me`.
2. Com esse token, `PUT /v1/system/app-status` com `{"app_status": false}`.
3. `GET /v1/articles` sem token → 503. Com o token de administrador → 200.
4. Pelo pgAdmin4, `UPDATE users SET admin = false WHERE email = '<email do dev>'`. Repita o passo 3 com
   o **mesmo** token: agora dá 503. É a prova de que a decisão vem do banco.
5. Volte a flag para `true` e religue a aplicação pelo passo 2 com `{"app_status": true}`.
