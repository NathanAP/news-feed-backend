# 0.41.0.0 — Split do docker-compose + hardening do pgAdmin

## Contexto

O `docker-compose.yaml` era único e incluía o pgAdmin. Duas consequências indesejadas:

1. Subir esse arquivo num servidor publicaria um painel de banco **sem login** (o pgAdmin roda em
   `SERVER_MODE=False`, modo desktop de usuário único — por isso ele abre direto no dashboard).
2. As portas eram publicadas sem prefixo de host (`5050:80`, `5432:5432`, `3000:3000`), ou seja, bind em
   `0.0.0.0` — qualquer máquina da LAN alcançava o pgAdmin (e caía direto no dashboard).

## O que mudou

### Split base + override

- **`docker-compose.yaml`** (base): os serviços compartilhados.
- **`docker-compose.override.yaml`** (novo, dev): o pgAdmin.

O Compose mescla os dois **automaticamente** no `docker compose up` — por isso `task ds`/`task dbs`
seguem sem flag nenhuma. O ponto de segurança: um arquivo de produção futuro é aplicado com `-f`
explícito, e **`-f` explícito desliga o auto-override**. Então o pgAdmin não vai pra produção por
**ausência** — ele nunca fez parte da base —, e não por alguém lembrar de removê-lo.

### Bind em loopback

Todas as portas publicadas passaram a `127.0.0.1:...`. Deixam de ser alcançáveis pela LAN. Um túnel
(ngrok, SSH) continua funcionando porque o processo do túnel roda **no próprio host** e conecta no
loopback — restringir o bind fecha a porta pra fora, não pro túnel local.

## Observação

Esta 0.41 pôs o `postgres` na base. A 0.42, ao introduzir staging/produção, moveu o `postgres` pra cada
overlay (base virou só a `api`), porque o Compose não consegue **remover** um serviço da base num
override e produção pode usar RDS em vez de container. É evolução iterativa, não correção de erro: o
objetivo da 0.41 (pgAdmin fora da base + bind loopback) continua valendo.

## Como testar

```bash
docker compose config --services          # dev: api, postgres, pgadmin4
docker compose config | grep host_ip      # todas em 127.0.0.1
```
