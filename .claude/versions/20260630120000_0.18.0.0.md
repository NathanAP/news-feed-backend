# Versão 0.18.0.0 — tabela `system` + guard de manutenção

**Data:** 2026-06-30

## Resumo

Painel de controle do sistema (tabela `system`, singleton) com a chave de manutenção global
`app_status`. Um middleware lê esse estado a cada requisição e bloqueia toda rota de negócio com
**503** quando a aplicação está desligada. Inclui a rota aberta `PUT /v1/system/app-status` para
ligar/desligar e o enriquecimento do `/v1/health` com `app_status` e `server_time`.

Esta versão é o resultado do **split** da antiga 0.18 (que também incluía CRON/descoberta/prompts).
A descoberta foi movida para a 0.19, e as versões seguintes foram renumeradas (+1) pelo usuário.

## Decisões aplicadas

- **`system` é singleton enxuto:** `id` (UUID v7), `app_status`, `last_article_discovery_at`
  (nullable), `created_at`, `modified_at`. **Sem** `status`/`removed_at` — uma chave de manutenção
  não é um registro soft-deletável; o próprio `app_status` é o interruptor. A tabela nunca recebe
  insert/delete por código: é semeada na migração e só sofre update.
- **`id` semeado como literal UUID v7 fixo:** o SQLite não gera UUID v7. Como é uma linha única,
  embutimos `01900000-0000-7000-8000-000000000001` com comentário explicando a exceção (mesmo
  espírito do backfill de `user_preferences`, mas aqui v7 e não v4).
- **Leitura do estado a cada requisição (sem cache):** o middleware relê a fonte da verdade (a
  linha `system`) via `WithTransaction`. Toggle no banco/endpoint reflete no próximo request, sem
  invalidação. Custo desprezível (SQLite, 1 linha, mesmo processo). Cache in-memory fica como
  otimização futura, se algum dia necessário.
- **Isenções do guard = `/health` + o próprio toggle.** Registradas **antes** do `api.Use(guard)`,
  então não são alcançadas pelo middleware. Isso é estrutural: sem isentar o toggle, a aplicação
  ficaria permanentemente trancada quando desligada. Todo o resto (inclusive `/auth/*`) retorna 503.
- **Guard roda antes da auth:** numa rota protegida, request sem token recebe **503** (não 401)
  enquanto a app está off — manutenção tem precedência sobre autenticação.
- **Toggle aberto (admin-futuro):** mesma postura das rotas `/auth/invalidate*`. Quando o usuário
  administrador existir, o guard passa a "admin não é afetado por manutenção; comum checa
  `app_status`" e fecham-se todas as rotas admin juntas (lembrete adicionado ao roadmap).
- **`/health` extraído para handler próprio** (`services/endpoints/v1/health/health.go`), antes era
  inline no `main.go`. Necessário porque agora lê o banco (`app_status`) e precisa ser testável.

## O que foi feito

### Banco de dados
- `migrations/20260630120000_create_system_table.sql` — cria `system` e semeia a linha única
  (`app_status=1`, `last_article_discovery_at` NULL). `down` dropa a tabela.
- `schema.sql` — espelho da tabela `system`.

### SQLC
- `sqlc/queries/system.sql` + `sqlc/system.sql.go`: `GetSystem` (`:one`, `LIMIT 1`) e
  `UpdateSystemAppStatus` (`:one`, `RETURNING *`).
- `sqlc/models.go` — struct `System`.
- `sqlc/querier.go` — `GetSystem` e `UpdateSystemAppStatus` adicionados à interface.

### Controllers / schemas
- `services/controllers/system.go` — `SystemController` (`Get`, `UpdateAppStatus`) + `ErrSystemNotFound`.
- `services/controllers/interfaces.go` — `SystemControllerInterface`.
- `schemas/system.go` — `UpdateAppStatusRequest` (`app_status *bool`, distingue ausente de false) e
  `SystemResponse`.

### Middleware / endpoints
- `middlewares/app_status.go` — `NewAppStatusMiddleware`: 503 quando `app_status=0`.
- `services/endpoints/v1/system/update_app_status.go` — `PUT /v1/system/app-status` → 200 / 400 / 500.
- `services/endpoints/v1/health/health.go` — `Check`: `{ status, version, app_status, server_time }`.
- `main.go` — `systemCtrl` instanciado; `/health` e `/system/app-status` registrados antes do
  `api.Use(NewAppStatusMiddleware(...))`; restante do grupo `/v1` protegido.

### Testes
- `tests/fixtures/system_fixtures.go` — `SetAppStatus(ctx, q, bool)`.
- **Unit (`tests/unit/system/`):** toggle aberto — sucesso enable/disable, campo ausente (400),
  body inválido (400), erro de DB (500).
- **Integração (`tests/integration/api/system/`):** health (snapshot + acessível em manutenção),
  guard (permite com app on; bloqueia antes da auth; bloqueia autenticado), toggle off→on com
  rota de negócio voltando a responder, campo ausente (400).
- **E2E (`tests/end-to-end/api/system/`):** fluxo de manutenção completo (healthy → login → cria
  source → off → 503 → religa estando off → volta a funcionar) + toggle sem campo (400).

### Bruno
- `bruno/system/update-app-status.bru` — `PUT /v1/system/app-status` documentado.
- `bruno/health.bru` — docs atualizadas com os novos campos.

### Controle de versão
- `.env.example` e `ROADMAP.md` → `0.18.0.0`; itens da 0.18 marcados como concluídos.

`go vet ./...` limpo e `go test ./tests/...` passando em todos os domínios (incluindo os novos
`unit/system`, `integration/api/system` e `end-to-end/api/system`).

## Notas para versões futuras

- **0.19 (descoberta):** a CRON deve checar `app_status` antes de rodar (o guard HTTP não cobre o
  job interno) e passará a atualizar `last_article_discovery_at` na linha `system`.
- **Usuário administrador:** trocar a isenção por rota pelo bypass-por-admin (admin não sofre
  manutenção; renovação de token durante manutenção sai naturalmente) e fechar as rotas admin.
