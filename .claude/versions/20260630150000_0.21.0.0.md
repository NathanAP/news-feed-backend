# Versão 0.21.0.0 — keywords via SLM (Ollama) + provider por tarefa

**Data:** 2026-06-30

## Resumo

O tratamento passa a usar **providers de IA distintos por tarefa**: o passo de melhora continua
numa **LLM** (Gemini) e a atribuição de **palavras-chave** vai para uma **SLM** local (Ollama,
`qwen3:4b`). A costura `ai.Client` foi quebrada em `ai.Treater` + `ai.Keyworder`, e adicionamos um
cliente OpenAI-compatible (serve Ollama hoje, qualquer endpoint compatível amanhã).

## Decisões aplicadas

- **Interface por capacidade.** `ai.Treater` (Treat) e `ai.Keyworder` (Keywords), com `ai.Client`
  como união pra providers que fazem os dois. Isso permite "ferramenta certa por tarefa" — cada
  tarefa escolhe seu provider independentemente.
- **Config por tarefa (env):** `TREATMENT_PROVIDER`/`TREATMENT_MODEL` e
  `KEYWORDS_PROVIDER`/`KEYWORDS_MODEL`. Substitui o `PRIMARY_AI_MODEL` interino da 0.20. Providers
  suportados (conventions.md): `google` (Gemini) e `ollama` (SLM via OpenAI-compatible).
- **Cliente OpenAI-compatible** (`services/ai/openaicompat`) em vez de um específico do Ollama:
  o mesmo cliente aponta pro Ollama local (`OLLAMA_BASE_URL`, default `http://localhost:11434`) ou
  pra qualquer servidor compatível (Groq/vLLM/...) só trocando a URL.
- **Gotcha do qwen3 (thinking):** o cliente remove blocos `<think>...</think>` antes de parsear —
  senão quebraria o JSON das keywords. Thinking off é o certo pra keywords (tarefa não-raciocínio).
- **Validação de keywords compartilhada:** `parseKeywords`/`stripCodeFence` saíram do pacote
  `gemini` para `services/ai` (`ai.ParseKeywords`), agora tolerando array **ou**
  `{"keywords":[...]}` **ou** code fence — reusada por todos os providers.
- **Docker adiado:** Ollama roda local em dev; entra no docker-compose só no deploy (0.23).
- **Cliente desabilitável mantido:** provider ausente/desconhecido → `ai.NewDisabledClient()`
  (falha clara por chamada), app sobe normalmente.

## O que foi feito

### Camada de IA
- `services/ai/ai.go` — `Treater`, `Keyworder`, `Client` (união), disabled client.
- `services/ai/keywords.go` — `ParseKeywords` compartilhada (array/objeto/code fence + 5–20 + dedup).
- `services/ai/gemini/gemini.go` — usa `ai.ParseKeywords`; segue implementando ambas as capacidades.
- `services/ai/openaicompat/openaicompat.go` — cliente OpenAI-compatible (`/v1/chat/completions`),
  retry/backoff/timeout 120s, strip de `<think>`.

### Fluxo
- `services/discovery/processor.go` — `TreatmentProcessor` recebe `Treater` + `Keyworder`.
- `services/endpoints/v1/articles/treatment.go` — `TreatArticle(treater, keyworder)`.
- `main.go` — `buildProvider(provider, model)` (factory: google→gemini, ollama→openaicompat,
  desconhecido→disabled); monta `treater` de `TREATMENT_*` e `keyworder` de `KEYWORDS_*`.

### Config
- `.env.example` — `OLLAMA_BASE_URL` adicionado (as vars por tarefa já existiam).

### Testes
- `services/ai/keywords_test.go` — `ParseKeywords` (movido do gemini; + caso objeto).
- `services/ai/openaicompat/openaicompat_test.go` — servidor HTTP fake: strip de `<think>`, parse
  de keywords, erro de status. Sem Ollama real.
- `tests/integration/discovery/processor_test.go` — `TreatmentProcessor` real com mock de IA + DB
  em memória: persiste tratado+keywords, deduplica `url_original`, falha de IA não persiste.
- `tests/unit/articles/treatment_test.go` — ajustado pra nova assinatura (`treater`+`keyworder`).

## Resultado dos testes

`go vet ./...` limpo e `go test ./...` sem falhas.

## Como testar localmente

1. `ollama serve` + `ollama pull qwen3:4b` (uma vez, ~2,5GB).
2. `.env`: `KEYWORDS_PROVIDER=ollama`, `KEYWORDS_MODEL=qwen3:4b`, `OLLAMA_BASE_URL=http://localhost:11434`;
   `TREATMENT_PROVIDER=google` + `GOOGLE_API_KEY` real (ou desabilitado, aí o tratamento falha claro).
3. `task ta` roda tudo com mocks (não precisa de Ollama). `task ls` sobe o app; a CRON/tratamento
   usam o Ollama de verdade pras keywords.
