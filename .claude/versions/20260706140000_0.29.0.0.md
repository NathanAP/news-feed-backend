# Versão 0.29.0.0 — client-readiness: feed articles + CORS + callback OAuth → frontend

**Data:** 2026-07-06

Preparação do backend para o client web (React + Vite). Três itens independentes, feitos em sequência
com confirmação entre eles.

## 1. `GET /v1/feeds/{id}/articles` — a tela central do produto

A rota que faltava: as notícias que caíram em um feed do usuário, cada uma com o seu `is_read`.

- **Query sqlc** `ListArticlesByFeedForUser` (`sqlc/queries/articles_feeds.sql` + gerado à mão em
  `sqlc/articles_feeds.sql.go` + `querier.go`): join `articles_feeds → feeds → articles`, escopado por
  `user_id` do feed, só ativos (feed e artigo), ordenado por `created_at DESC`, trazendo `af.is_read`.
- **Controller** `ArticleFeedController.ListArticlesByFeedForUser` (+ interface).
- **Handler** `services/endpoints/v1/feeds/articles.go`: checa a posse do feed primeiro
  (`FeedController.FindByID` → 404 se inexistente ou de outro usuário), depois filtra e pagina.
  - Filtros: `is_read` (`true`/`false`) e janela `period_starting_at`/`period_ending_at`
    (RFC3339 UTC, ambos inclusivos e independentes) sobre `articles.created_at`.
  - **Decisão:** filtro `is_read`/período **em Go** sobre a lista base do SQL, e paginação em memória
    (`pagination.Paginate`). Coerente com o resto do projeto (todo list endpoint carrega a base e
    refina em Go; paginação em memória documentada até o Postgres). SQL-pushdown de filtro+paginação
    ficou registrado no ROADMAP futuro.
  - **Resposta:** reusa `schemas.ArticleResponse` (que já tem `is_read`), sem DTO novo. Aqui `is_read`
    é sempre definido (a notícia está no feed), nunca `null`.
- 404 (feed inexistente/de outro usuário) vs 200 com `docs` vazio (feed do usuário sem notícias).
- Testes: unit (404, 400 em `is_read`/data inválida, filtros, envelope, 500), integração (join real,
  `is_read` do banco, 404 cross-user, vazio, não-encontrado, 401) e um E2E no fluxo. Bruno:
  `get-feed-articles.bru`.

## 2. CORS

- `middlewares/cors.go` (`NewCORSMiddleware`): lê `CORS_ALLOWED_ORIGINS` (lista separada por vírgula,
  origins completas com esquema). `AllowMethods` GET/POST/PUT/DELETE/OPTIONS, `AllowHeaders`
  `Authorization, Content-Type`. **Sem `AllowCredentials`** — auth é Bearer, não cookie.
- Vazio → **fail-closed** (middleware no-op, sem cair para o `*` padrão do Fiber) + aviso no log.
- Registrado em `main.go` **antes de tudo** (cobre preflight `OPTIONS`, `/health` e o guard de
  manutenção).
- Nova env `CORS_ALLOWED_ORIGINS` no `.env.example`. Testes em `tests/integration/cors/`.

## 3. Callback OAuth → frontend (com `state` assinado e allowlist)

Reescrita do login para devolver o usuário ao client, em vez de responder JSON.

- **Novo pacote puro `services/oauthstate`** (`Generate`/`Validate`): o `state` é um JWT HS256 curto
  (10 min) assinado com o segredo do app, carregando o `redirect_uri` + um nonce. É CSRF **e** o
  veículo que leva o `redirect_uri` pela ida-e-volta do Google (HTTP é stateless). Teste co-localizado
  (mesmo padrão de `langdetect`/`sanitize`). Feito como pacote à parte para **não inchar a
  `AuthControllerInterface`** nem seus mocks.
- **`GET /v1/auth/google`** (`GoogleLogin`): exige `redirect_uri`, valida por **match exato** contra a
  allowlist (`OAUTH_ALLOWED_REDIRECT_URIS`) — senão 400 e **nunca** redireciona (evita open-redirect).
  Assina o `state` e redireciona ao Google com o callback fixo.
- **`GET /v1/auth/google/callback`** (`GoogleCallback`): valida o `state` (401 se inválido/expirado),
  recupera o `redirect_uri` confiável; se o Google retornou `error` (cancelamento) → redireciona ao
  client com `?error=`; senão troca o `code` (401 se falhar) e redireciona ao `redirect_uri` com os
  tokens no **fragment** (`#access_token=...&refresh_token=...&expires_in=...`).
- Status codes (conforme `PROJECT.md`): `redirect_uri` inválido → 400; `state`/troca de `code` falha →
  401; cancelamento → redirect com `?error=`.
- Nova env `OAUTH_ALLOWED_REDIRECT_URIS` no `.env.example`. Helper `parseCSV` no `main.go`.

### Ripple nos testes (grande)

O callback deixou de responder JSON e passou a exigir `state`, então todo o login de teste mudou:
- Novo helper compartilhado `tests/utils/oauth.go` (`CompleteOAuthLogin` + `ParseTokensFromRedirect`,
  const `TestOAuthRedirectURI`): minta um `state` válido, chama o callback e lê os tokens do fragment.
- Auth **unit** e **integração**: reescritos (`GoogleLogin`/`GoogleCallback` novas assinaturas; casos
  de `state` ausente/inválido, cancelamento, fragment).
- Auth **E2E**: `loginViaCallback` agora faz o **fluxo de dois passos** real (`/auth/google` → extrai
  `state` → callback → fragment).
- E2E de feeds/articles/sources/system: registro do callback com o segredo + `loginViaCallback`
  usando o helper compartilhado.

## Como testar

- **Feed articles:** `task sdfull` (seed) e `GET /v1/feeds/{id}/articles` com `Authorization: Bearer`;
  testar `?is_read=true|false` e `?period_starting_at=...&period_ending_at=...`.
- **CORS:** subir a API com `CORS_ALLOWED_ORIGINS=http://localhost:5173` e um client React nessa
  origem; requests cross-origin passam. Origem fora da lista é bloqueada pelo browser.
- **Login:** abrir no browser `GET /v1/auth/google?redirect_uri=<allowlistada>`; ao final, o browser
  aterrissa no `redirect_uri` com os tokens no fragment. `redirect_uri` fora da allowlist → 400. É
  preciso registrar o callback fixo no Google Cloud Console (Credenciais → URIs de redirecionamento).
