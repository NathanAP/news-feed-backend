# 0.37.2.0 — `CORS_ALLOWED_HEADERS` configurável

Destrava o client no Vercel, que não conseguia falar com a API pelo túnel, e de passagem corrige uma
inconsistência do próprio middleware de CORS.

## O sintoma

O client em `https://news-feed-client-zeta.vercel.app` recebia:

```
Access to XMLHttpRequest ... blocked by CORS policy:
No 'Access-Control-Allow-Origin' header is present on the requested resource.
GET https://<dev-domain>.ngrok-free.dev/v1/feeds net::ERR_FAILED 200 (OK)
```

Parecia CORS mal configurado, mas não era: o `CORS_ALLOWED_ORIGINS` estava correto e a API, testada
direto no `localhost:3000` com o `Origin` do Vercel, devolvia o header certinho. Pelo túnel via curl,
também. O `200 (OK)` num request que "falhou" era a pista.

## A causa

A **interstitial do ngrok** (`Ngrok-Error-Code: ERR_NGROK_6024`). No plano free, o ngrok intercepta
qualquer requisição com **User-Agent de browser** e devolve uma página de aviso em HTML — status 200,
`Content-Type: text/html`, **sem nenhum header de CORS**. O gatilho é o User-Agent, não o tipo de
navegação, então o XHR do client (que sai com UA de Chrome) era interceptado igual.

O que tornava o diagnóstico contraintuitivo: o **preflight OPTIONS passava** (204, com todos os
headers), porque a interstitial não intercepta OPTIONS. O browser liberava, fazia o GET de verdade, e
esse levava a página de aviso. Daí a mensagem de CORS num problema que não era de CORS.

Isolamento que apontou a causa: mesma requisição, direto na API → header presente; pelo túnel com UA
de curl → header presente; pelo túnel com UA de Chrome → HTML do ngrok, 200, sem header.

## A correção

O jeito documentado de escapar da interstitial é o client enviar `ngrok-skip-browser-warning`. Só que
**um header que o preflight não permite é um header que o browser se recusa a enviar** — e o
`AllowHeaders` estava hardcoded como `Authorization,Content-Type` no `middlewares/cors.go`, enquanto o
`AllowOrigins` já vinha de env. Essa assimetria era a inconsistência real.

- **`CORS_ALLOWED_HEADERS`** (novo): lista de headers que o client pode enviar. Vazio/ausente cai no
  default `Authorization,Content-Type` — quem nunca ouviu falar da variável continua com um client
  funcionando.
- `.env.example` traz o `ngrok-skip-browser-warning` **com o motivo escrito** e a instrução de removê-lo
  quando não houver túnel no caminho.
- 4 testes novos em `tests/integration/cors/`: default quando ausente, override honrado, header fora da
  lista não é anunciado, e um helper `preflight` que faz os testes lerem como a conversa do browser.

Verificado simulando a troca exata do browser pelo túnel: preflight → 204 com o header do ngrok
liberado; GET com UA de Chrome + o header → JSON da API (não a HTML) com `Access-Control-Allow-Origin`.

## O que fica do lado do client (não é deste repo)

O client precisa enviar `ngrok-skip-browser-warning: true`, **condicionalmente**: em produção, sem
túnel, a API não vai permitir esse header e o preflight quebra. Deve depender da URL base da API ser o
túnel.

## Correção de um conselho errado que eu tinha dado

Antes eu havia dito que bastava "abrir a URL do ngrok no navegador uma vez e clicar para passar". Isso
resolve para **navegação direta** (o clique grava um cookie no domínio do ngrok), mas **não** para o
XHR do client: a chamada é cross-origin a partir do `vercel.app` e não envia credenciais, então o
cookie nunca acompanha. Registrado aqui para não voltar como sugestão.

## Alternativa considerada e não adotada

Trocar o ngrok por um túnel sem interstitial (Tailscale Funnel). Resolveria sem header nenhum, mas
exigia instalar outra ferramenta e re-apontar a URL base — e o `CORS_ALLOWED_HEADERS` se justifica
sozinho, independentemente de túnel. Os dois caminhos continuam abertos: o Google Console aceita
vários redirect URIs registrados ao mesmo tempo, então migrar depois é trocar uma variável.
