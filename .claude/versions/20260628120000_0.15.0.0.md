# Versão 0.15.0.0 — Feeds

**Data:** 2026-06-28

## Resumo

Domínio de **feeds**: registros de palavras-chave criados e geridos por cada usuário. É o **primeiro recurso por-usuário** com proteção cross-user (feed de outro usuário responde 404, não 403). Inclui o limite de 5 feeds ativos por usuário e o cascade soft `user→feeds`. A junction `articles_feeds` e o `mark-as-read` ficaram para a 0.16 (split combinado).

## O que foi feito

### Banco de dados
- `migrations/20260628120000_create_feeds_table.sql` — tabela `feeds` (`id`, `status`, `name`, `keywords` JSON array TEXT default `'[]'`, `user_id`, timestamps), PK `id`, FK `user_id → users(id)`. Sem índice de unicidade (nomes duplicados permitidos).
- `schema.sql` atualizado.

### SQLC (todas as queries user-scoped)
- `sqlc/queries/feeds.sql` + `sqlc/feeds.sql.go`: `CreateFeed`, `FindFeedByIDAndUser`, `ListFeedsByUser`, `CountActiveFeedsByUser`, `UpdateFeedByIDAndUser`, `SoftDeleteFeedByIDAndUser`, `SoftDeleteFeedsByUser`.
- `sqlc/models.go` — struct `Feed`. `sqlc/querier.go` — métodos adicionados.
- O par `id + user_id` no `WHERE` é o que torna o feed de outro usuário "inexistente" → 404.

### Controllers
- `services/controllers/feeds.go` — `FeedController` (Create/FindByID/List/Update/SoftDelete), todos recebendo `userID`. O `Create` checa o limite de 5 ativos via `CountActiveFeedsByUser` (na mesma transação) → `ErrFeedLimitReached`. Reuso do `encodeKeywords`/`DecodeKeywords` já existentes.
- `services/controllers/interfaces.go` — `FeedControllerInterface`.
- `services/controllers/users.go` — `SoftDeleteUser` ganha o cascade **soft** `user→feeds` (via `SoftDeleteFeedsByUser`). Sem rota que dispare (não há delete-user); mantido correto para o futuro.

### Schemas
- `schemas/feeds.go` — `CreateFeedRequest`, `UpdateFeedRequest` (sem `user_id`, imutável), `FeedResponse`. Constantes: keywords 5–20, name ≤ 120, máximo 5 feeds/usuário.

### Endpoints (`/v1/feeds`, autenticados, `user_id` do JWT)
- `POST /create` → 201 / 400 (name vazio/>120, keywords fora de 5–20 ou com vazio) / 409 (limite) / 500
- `GET /:id` → 200 / 404 (inexistente ou de outro usuário) / 500
- `GET ?name=...` → 200 (só os próprios feeds) / 500
- `PUT /:id` → 200 / 400 / 404 / 500
- `DELETE /:id` → 204 / 404 / 500 (soft delete, find-before-delete por id+user)
- `main.go` registra as 5 rotas no grupo `/v1/feeds`.

### Testes
- `tests/fixtures/feed_fixtures.go` — `NewTestFeed`, `NewTestFeedAlt`, `ValidFeedKeywords`.
- **Unit:** todas as rotas + validações (name, keywords, limite via mock), 404 cross-user, auth.

## Decisões de design

- **Recurso por-usuário com 404 (não 403):** o `user_id` entra no `WHERE` das queries, então feed de outro usuário é indistinguível de inexistente — não vaza existência.
- **Limite de 5 no controller:** precisa de `COUNT` no banco, então é regra de negócio no controller, contada na mesma transação do insert (sem corrida).
- **Exclusão permanente:** soft delete sob o capô (necessário para invisibilidade futura na junction), mas sem reativação — conforme PROJECT.md.
- **Cascade hard `user→feeds`:** não implementado — não existe hard remove de usuário no código (item futuro no ROADMAP).
