# 0.37.1.0 — UTC no sistema de tipos (Etapa 4 da 0.37) + correção de flakiness nos testes

Fecha a dívida que a 0.37.0.0 assumiu conscientemente e corrige uma fragilidade nos testes que a
0.37.0.0 introduziu sem que ninguém percebesse.

**Por que `patch` e não parte da 0.37.0.0**: a Etapa 4 estava escrita dentro da seção 0.37.0.0 do
ROADMAP, mas a 0.37.0.0 já tinha sido declarada concluída, com arquivo em `versions/` e marcador de
versão movido. Acrescentar código a uma versão já fechada faria o registro mentir sobre o que
entregou o quê e quando.

## O problema (recapitulando)

O pgx entrega um `TIMESTAMPTZ` escaneado como `time.Time` no fuso **local do processo**. Numa máquina
em -03:00 a API serializava `2026-07-16T15:01:13-03:00` em vez de `...Z`: instante certo,
representação errada. E — o pior — **variando conforme o host**: um servidor em UTC esconderia o bug
por completo, até alguém subir num host com outro fuso e o client quebrar sem ninguém ter mexido em
código. Não era peculiaridade de estar no Brasil; estar no Brasil só **revelou**.

A 0.37.0.0 corrigiu com `time.Local = time.UTC` no `main.go` e no seed. Funciona, mas: é mutação de
global do runtime, a garantia fica invisível no ponto de uso, e **todo entrypoint novo precisa
lembrar da linha** — o `cmd/seed` já tinha precisado. Eram dois; o terceiro era questão de tempo.

## O que mudou

- **Novo pacote `services/utctime`**: `Time` e `NullTime`. O `Scan` converte para UTC na fronteira
  (uma vez, não em cada chamador), o `Value` normaliza na escrita, o `MarshalJSON` sempre emite `Z` e
  o `UnmarshalJSON` aceita e normaliza um offset recebido. `NullTime.Ptr() *time.Time` mapeia uma
  coluna anulável direto no `*time.Time` dos schemas. 12 testes co-localizados (lógica pura), usando
  uma zona fixa `-03` para reproduzir a condição que gerava o bug.
- **`sqlc.yaml`**: `overrides` de `timestamptz` (e do nullable) para esses tipos. Todo model e row
  gerado passou a usá-los.
- **`time.Local = time.UTC` removido** do `main.go` e do `cmd/seed` — a dívida quitada.
- **`log.SetFlags(log.LstdFlags | log.LUTC)`** no `main.go`: sem o `time.Local`, o logger padrão
  voltou a carimbar em fuso local, e o log dizia 16:08 ao lado de uma resposta dizendo 19:08Z. Não é
  cosmético — é uma armadilha para quem lê os dois juntos.
- **`logger.go`**: `now()` ganhou `.UTC()` explícito.
- **`schemas.Claims.CreatedAt` virou `utctime.Time`** — exceção deliberada à regra "schemas ficam com
  `time.Time`". É valor de wire que o client lê do payload do token, e estava demonstravelmente
  errado: o JWT emitido trazia `...-03:00`. Aqui é o tipo que mantém o token honesto.
- **Simplificações**: `toSystemResponse` caiu de 16 para 8 linhas, e os blocos
  `if x.ModifiedAt.Valid { t := ...; resp.X = &t }` viraram `x.ModifiedAt.Ptr()` em todos os
  endpoints. `SystemController.UpdateLastArticleDiscovery` perdeu o `at.UTC()` manual.

## Decisão de escopo: os schemas continuam com `time.Time`

O tipo garante a fronteira banco→Go, que é onde o bug estava; depois dela o valor já é UTC. Levar o
tipo até os schemas protegeria contra alguém enfiar um `time.Now()` local numa resposta — mas a
auditoria das 16 chamadas de `time.Now()` achou **zero** ocorrências disso, e custaria ripple em
fixtures e testes. A auditoria (registrada em `conventions.md`): as de `ai/verbose.go`,
`treatment.go` e `judgement.go` só medem duração; as de `auth.go`/`oauthstate.go` viram
`jwt.NewNumericDate`, que é epoch em segundos; `cron.go` e `health.go` já chamavam `.UTC()`.

## Correção de flakiness nos testes (bug da 0.37.0.0)

A suíte passou duas vezes na 0.37.0.0 e depois começou a falhar de forma intermitente — **3 falhas em
5 execuções**, num pacote diferente a cada vez, todas em 0.00s (falha de setup, não de lógica). Erro:

```
failed to start the postgres container: get provider:
rootless Docker is not supported on Windows, failed to create Docker provider
```

Causa: sem `DOCKER_HOST` no ambiente, o testcontainers percorre uma cadeia de fallbacks para achar o
daemon (properties → contexto do Docker → socket padrão → **rootless**, que no Windows é erro final).
O `go test` roda os pacotes em paralelo, então ~14 processos leem o contexto do Docker no mesmo
instante; quem perde a corrida cai até o fim da cadeia. Retry **não** resolveu (a resolução falha
igual em toda tentativa dentro do mesmo processo).

Correção: `pinDockerHost()` no bootstrap de teste pergunta o endpoint ao próprio Docker
(`docker context inspect`) e fixa `DOCKER_HOST`, curto-circuitando a cadeia. Cross-platform (npipe no
Windows, socket unix no resto) em vez de hardcode por SO; se a consulta falhar, deixa como estava.
O retry ficou para o outro lado da mesma rajada: dois processos disputando a criação do container.

Validação: **6 execuções a frio, 0 falhas** (antes: 3 falhas em 5).

## Verificação

Com a máquina em `E. South America Standard Time` (-03:00) e **sem** o `time.Local`:

- `GET /v1/feeds` → `"created_at":"2026-07-16T18:01:13.613098Z"`
- `GET /v1/health` → `"server_time":"2026-07-16T19:12:26Z"`
- payload do JWT → `created_at: 2026-07-16T18:01:13.564201Z` (antes: `...15:01:13.564201-03:00`)
- logs de boot carimbando em UTC, concordando com as respostas

Suíte: 31 pacotes verdes.
