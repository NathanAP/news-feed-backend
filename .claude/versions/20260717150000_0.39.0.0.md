# 0.39.0.0 — Sugestão de palavras-chave

Endpoint novo que ajuda o usuário a montar um feed sugerindo palavras-chave para adicionar, tiradas
do acervo global de notícias.

## Motivação de produto (a decisão central desta versão)

O objetivo **não** é sugerir só termos "precisos". É o contrário: o endpoint existe para empurrar o
usuário a escolher **palavras-chave genéricas** (`rock`, `concerts`, `albums`, `music`). O raciocínio,
alinhado com o dono do projeto:

- O específico a pessoa lembra sozinha ("quero Metallica").
- O genérico é o que ela **esquece** — e é justamente o que faz a notícia bater no feed na camada 1 do
  julgamento (overlap exato de keywords). Um feed só de específicos recebe pouca notícia.

Por isso o ranking é por **contagem de ocorrência crua**, sem penalizar genéricos. Foi uma escolha
consciente, discutida e registrada — não uma simplificação por falta de tempo. Ranking mais fino
(lift / peso por especificidade) fica para quando houver volume real de feeds para calibrar, porque
hoje (poucos artigos) qualquer piso de suporte seria chute.

## Endpoint

`GET /v1/feeds/keyword-suggestions?keywords=metallica,rock&limit=10` (autenticado).

Fica sob `/feeds` porque é o que ele serve (montar feed), embora o dado venha de `articles` — por isso
o handler recebe `articleCtrl`, não `feedCtrl`. Registrado **antes** de `/:id` para não ser engolido
como um id (mesmo cuidado de `check-for-new-articles`).

Resposta:
```json
{
  "strategy": "related",
  "suggestions": [ { "keyword": "rock", "count": 812 }, { "keyword": "concerts", "count": 133 } ]
}
```

A `strategy` é ecoada de propósito: o client rotula a lista ("Relacionadas às suas escolhas" vs
"Populares agora") e o fallback fica observável sem ler log.

### Query params (todos opcionais)

- `keywords`: as escolhidas, separadas por vírgula. Normalizadas no servidor (trim, minúsculas,
  dedupe, vazias descartadas). Mais que `FeedKeywordsMax` (20) → 400 (não pode passar do teto de um
  feed, e também limita o tamanho do array `?|`).
- `limit`: quantas trazer. Padrão 10, faixa [1, 50]. Nunca erra — inválido cai no padrão, é clampado
  (mesma filosofia do `pagination.ParseParams`).

### Duas estratégias, com fallback

- `related` (há keywords escolhidas): keywords que mais **co-ocorrem** com as escolhidas (aparecem nas
  mesmas notícias). É topical, **não janelada**: relatedness não tem a ver com tempo, e janelar só
  faria o fallback disparar mais para um pick de nicho. Query `SuggestRelatedKeywords`.
- `popular` (nada escolhido, **ou** related veio vazio): keywords mais frequentes nas notícias
  **recentes**. Query `SuggestPopularKeywords`.
- **Nunca fica sem sugestão**: related vazio → cai em popular (roadmap). A keyword já escolhida nunca é
  sugerida de volta, nas duas estratégias (o `exclude`/`selected` cobre isso).

### Janela de tempo (`KEYWORD_SUGGESTIONS_WINDOW_DAYS`)

Só afeta `popular`. Padrão 30 dias; `-1` desliga (todo o histórico). Existe por dois motivos:

- **Produto**: "popular" deve significar "popular agora", não uma keyword quente em 2024.
- **Custo**: `popular` é uma agregação da tabela inteira (expande as keywords de todas as notícias
  ativas). A janela é o que a mantém limitada. Medição de referência da 0.38: um `COUNT(*)` pelado em
  100k artigos já toca ~3400 buffers; isto é aquilo somado à explosão de ~30x em linhas do
  `jsonb_array_elements_text` mais o `GROUP BY`. A janela corta o `N` antes de tudo isso.

O `since` é resolvido por requisição (`now - janela`, ou epoch quando desligada), sempre em UTC.

## Migração: índice GIN em `articles.keywords`

`idx_articles_keywords` (`USING GIN (keywords)`), espelhando o de `feeds.keywords`. A query `related`
usa `keywords ?|` para narrar as notícias antes de expandir — e é o operador `?|` que alcança o índice
(a mesma lição da 0.37.3, onde o índice existia mas nenhum operador o alcançava).

**Verificado por `EXPLAIN`** (não confiei na teoria): com `enable_seqscan=off` o plano vira
`Bitmap Index Scan on idx_articles_keywords` com `Index Cond: (keywords ?| ...)`. Ou seja, o índice é
**alcançável** — não é peso morto como o caso da 0.37.3. Em tabela pequena e cacheada o planner
prefere seq scan (decisão de custo correta); o índice entra em ação quando o volume cresce e o
predicado é seletivo. Migração justificada.

## Arquitetura / código

- **Queries** (`sqlc/queries/articles.sql`): `SuggestPopularKeywords`, `SuggestRelatedKeywords`. Ambas
  expandem com `LATERAL jsonb_array_elements_text`, agrupam, contam, e ordenam por
  `occurrences DESC, keyword ASC` — o desempate por `keyword` é a lição da 0.38 (sem ele, empate de
  contagem sai em ordem arbitrária e a resposta vira não-determinística). O `::text` no `SELECT` é
  necessário para o sqlc tipar a coluna como `string` (sem ele vira `interface{}`).
- **Controller** (`ArticleController.SuggestKeywords`): decide related-com-fallback-para-popular,
  normaliza os picks via `encodeKeywords`, e devolve `([]schemas.KeywordSuggestion, strategy, error)`.
  Resultado vazio é legítimo (banco novo), não é erro.
- **Schema** (`schemas/keyword_suggestions.go`): DTOs de resposta + constantes (limites, strategy).
- **Handler** (`services/endpoints/v1/feeds/keyword_suggestions.go`): parse/validação da query
  (`parseSelectedKeywords`, `parseSuggestionLimit`, `suggestionSince`) e montagem do envelope.
- **main.go**: `parseSuggestionWindowDays` (segue o padrão do `parseMaxArticles`), rota registrada
  antes de `/:id`.

## Convenção ajustada

`conventions.md` diz que endpoint de busca por múltiplos parâmetros **sempre** pagina. Este é um
**indicador ranqueado**, não uma listagem de registros — usa `limit` simples, sem `page`/`page_size`.
Registrei a isenção no `conventions.md` e no `PROJECT.md` (a mesma que `check-for-new-articles` já
tinha de fato, e que o `PROJECT.md` dá a "relatórios, métricas, indicadores ou afins"). `OFFSET` sobre
agregação é caro e ninguém navega até a página 5 de sugestões.

- **Unit** (`tests/unit/feeds/keyword_suggestions_test.go`): o que o handler owna — normalização dos
  picks, `keywords` ausente = seleção vazia, >20 picks = 400, clamp do `limit`, resolução da janela em
  `since` (positiva ≈ now-janela; negativa = epoch), shape do envelope, erro do controller = 500.
- **Integração** (`tests/integration/api/feeds/keyword_suggestions_test.go`): a lógica SQL contra
  Postgres real — ranking popular por contagem, related por co-ocorrência com desempate alfabético,
  fallback related-vazio→popular, fallback ainda excluindo o pick, banco vazio = `[]` (não `null`),
  `limit`, soft-deleted fora da contagem, 401.

- Mocks: a nova assinatura de `ArticleControllerInterface.SuggestKeywords` propagou para os mocks
  manuais em `tests/unit/{articles,sources}` (no-op) e um mock dedicado no unit de feeds.

## Como testar

```bash
task dbs && task ls && task sdfull   # sobe banco+API, popula, imprime token
```

Com o token:

- `GET /v1/feeds/keyword-suggestions` — populares (nada escolhido).
- `GET /v1/feeds/keyword-suggestions?keywords=metallica` — relacionadas; `strategy` deve virar
  `related` e `metallica` não aparece na lista.
- `GET /v1/feeds/keyword-suggestions?keywords=termo-que-nao-existe` — `strategy` cai para `popular`
  (fallback).
- `GET /v1/feeds/keyword-suggestions?limit=3` — no máximo 3 sugestões.

Para ver o índice em ação em escala, seguir o método da 0.38 (seed de ~100k artigos + `EXPLAIN
ANALYZE` da query related com uma keyword seletiva).
