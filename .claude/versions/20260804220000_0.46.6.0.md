# 0.46.6.0 — SSRF no `rss-discovery` + rota para administrador

## Resumo

Fecha as duas decisões deixadas em aberto pela 0.46.5.0. Nenhuma era defeito — eram escolhas de
produto, e ambas foram tomadas.

## 1. Bloqueio de destinos privados (SSRF)

`GET /v1/sources/rss-discovery` é a única rota que busca uma URL fornecida por quem chama. Isso é uma
primitiva de server-side request forgery: dá para apontá-la para o loopback, para o endpoint de
metadados da nuvem ou para faixas privadas que o processo alcança e o chamador não deveria.

**O controle ficou no dialer, não na validação da URL**, e essa escolha é o ponto central:

- **Um hostname não é um endereço.** `evil.example.com` pode resolver para `127.0.0.1`, então
  inspecionar a string da URL não prova nada sobre onde a conexão vai parar.
- **Redirect escapa de qualquer validação de URL.** Uma URL pública respondendo 302 para
  `http://169.254.169.254/...` passaria por qualquer checagem feita antes da primeira requisição. Cada
  salto abre uma conexão nova, então cada salto passa pelo dialer.

Pacote novo `services/safehttp`, com `NewRestrictedClient`. Depois de resolver o nome, ele disca o **IP
já aprovado** em vez de devolver o hostname ao dialer — re-resolver abriria uma janela para a segunda
consulta retornar um endereço diferente do que acabou de ser aprovado (DNS rebinding). Um nome que
resolve para endereços públicos **e** privados é recusado por inteiro, porque é exatamente disso que
uma tentativa de rebinding se parece.

Recusados: loopback, RFC1918 e `fc00::/7`, link-local (que inclui o `169.254.169.254`), multicast,
unspecified, CGNAT (`100.64.0.0/10`, que o `net.IP.IsPrivate` não cobre) e `0.0.0.0/8`.

Testes cobrem o veredito por faixa sem discar nada, mais três casos de conexão real: servidor em
loopback recusado, redirect para loopback recusado, e o endereço literal de metadados recusado.

O `discoveryHTTPClient` (usado pelo `article-discovery` e pela CRON) **não** mudou: ele busca a URL de
uma source que um administrador curou e gravou, que é uma origem diferente.

## 2. Rota passa a ser administrator-only

Alinha com o irmão `article-discovery`, que já era. O motivo de estar aberta era conveniência do
Bruno, não intenção de produto — descoberta não é ação de usuário final. Quando a rota de "sugerir uma
fonte" do roadmap existir, é lá que o acesso de usuário comum pertence.

O Bruno segue funcionando: em dev, `task sdl`/`task sdfull` emitem token de administrador. A
documentação da requisição foi atualizada com isso e com as duas restrições do cliente HTTP.

Testes: e2e e unit passaram a registrar a rota com a cadeia de admin (espelhando o `main.go`), e o
caso `rss-discovery` entrou na tabela de `TestE2E_Sources_RegularUserReadsButCannotWrite`, que prova
403 para usuário comum. Sem esse acréscimo a mudança ficaria sem cobertura.

## Lacuna registrada, não corrigida

`tests/integration/api/sources/sources_test.go` não modela autorização de administrador em rota
**alguma** — registra `create`, `update`, `delete` e as duas descobertas todas com a cadeia de auth
simples. Não é regressão desta versão (é como o arquivo sempre foi), e a autorização está coberta em
unit e e2e. Mas significa que aquele arquivo aceita requisições que a produção recusaria. Mudar isso
exige semear usuário administrador em cada teste dali; fica como candidato para depois da revisão.
