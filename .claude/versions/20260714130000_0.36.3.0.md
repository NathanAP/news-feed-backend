# Versão 0.36.3.0 — cap de notícias por varredura (freio de rate limit em dev)

**Data:** 2026-07-14

Pequeno freio para testar a CRON contra o Groq sem estourar o rate limit: quando uma fonte traz muitas
notícias de uma vez (a Wikimetal solta ~20), a varredura disparava um monte de chamadas de IA
(keywords + julgamento) no mesmo minuto. Agora dá para limitar quantas notícias uma varredura processa.

## O que mudou

- Nova env **`DISCOVERY_MAX_ARTICLES`** (int, default **`-1` = sem cap**, que é o valor de produção). Se
  `>= 0`, o `DiscoveryRunner` corta o lote combinado da varredura para esse tamanho **antes** de
  entregar ao `processor.Process` (portanto antes do tratamento/julgamento).
- `main.go` lê a env com `parseMaxArticles` (fallback `-1` em valor inválido, sem crashar) e injeta no
  `NewDiscoveryRunner` (novo parâmetro `maxArticles`).
- Log (verbose): `@@@ DISCOVERY CAP - processing N of M discovered item(s) @@@` quando o cap corta.

## Caveats (documentados)

- É um corte **bruto da lista crua**, antes do dedup por `url_original`. Ou seja, limita "quantas
  notícias a varredura olha". Para uso de teste é exatamente o desejado; em produção fica `-1`.
- Como corta a lista da fonte, os itens além do cap só entram numa varredura futura conforme a lista da
  RSS muda. Aceitável para o propósito (freio de dev).

## Testes

- `tests/integration/cron/discovery_test.go`: novo `CapsBatchWhenMaxArticlesSet` (fonte com 3 itens,
  cap 2 → processor recebe 2). Demais testes passam `maxArticles=-1` (sem cap, comportamento inalterado).
- `go build`, `go vet`, `gofmt -l`, `go test ./...` — **verdes**.

## Docs

`PROJECT.md` (lista de envs da descoberta), `memory/endpoints.md` (CRON), `.env.example`
(`DISCOVERY_MAX_ARTICLES=-1`). ROADMAP com a 0.36.3.0.

## Como testar

Com `RSS_FEED_CRON_ACTIVE=true`, `RSS_FEED_CRON_SCHEDULE=@every 30s`, `RSS_FEED_CRON_VERBOSE_MODE=true` e
`DISCOVERY_MAX_ARTICLES=3`: `go run main.go`. Na varredura, o log mostra o cap e só 3 notícias entram no
tratamento/julgamento, mesmo que a fonte tenha 20. Com `-1`, processa todas.

## Aberto (discutido, não implementado)

O gargalo estrutural do **julgamento** (nº de chamadas/tokens escala com `notícias × feeds candidatos`)
continua aberto. Batching (1 chamada por notícia) não basta sozinho porque com muitos feeds a requisição
fica gigante. A direção acordada é usar o **overlap de keywords** (barato, SQL) para auto-decidir o grosso
(ex.: auto-associar quando o artigo cobre ≥X% das keywords do feed) e mandar à IA só a faixa "borderline".
Próxima versão a planejar.
