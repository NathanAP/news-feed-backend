# Versão 0.10.1.0 — Revisão: padrão de transações (WithTransaction)

Refatoração nascida de uma revisão geral de código (modelo Opus 4.8). Não adiciona
features — corrige a forma como o projeto lida com transações de banco, além de
limpezas de robustez identificadas na revisão.

## Motivação

A revisão encontrou um risco crítico: `CreateUser` gravava o usuário e depois as
preferências sem transação. Uma falha parcial deixaria um usuário órfão (sem
preferências), e como o login exige preferências para montar o token, aquela conta
ficaria permanentemente impedida de logar. O mesmo padrão se repetiria em todo fluxo
multi-escrita futuro (categorias + fontes, etc.).

A decisão foi padronizar o controle de transações em vez de tratar cada caso à mão.

## Padrão adotado

- **Controllers nunca commitam.** Todos os métodos (escrita e leitura) recebem um
  `db.Querier` e são apenas passos intermediários — operam sobre a querier que recebem.
- **Quem orquestra o caso de uso é dono da transação.** A transação é aberta uma única
  vez no topo (rota, middleware ou caso de uso) e commitada/rollbackada por
  `WithTransaction`.
- **Composição natural:** como o método recebe a querier, o mesmo código roda sozinho
  (autocommit) ou dentro de uma transação maior. Ex.: criar 50 usuários numa transação
  só = um `WithTransaction` em volta de 50 chamadas, um único commit, rollback total se
  qualquer uma falhar.
- O `database/sql` do Go não suporta transação aninhada, por isso a regra "abre uma vez
  no topo". Para fluxos com I/O externo (callback do Google), a transação envolve só as
  gravações — a chamada de rede fica fora.

## Mudanças

### Novo: `services/controllers/transaction.go`

- `WithTransaction(ctx, database, fn)` — abre a transação, roda `fn(db.New(tx))`, commita
  no sucesso, rollback no erro. Único dono do commit/rollback.
- `TransactionRunner` (tipo) + `NewTransactionRunner(database)` — versão injetada, para
  que os testes unitários possam usar um substituto sem banco.

### Controllers (todos os métodos recebem `q db.Querier`, sem commit)

- `UserController` — agora stateless; `CreateUser` (usuário + preferências) e
  `SoftDeleteUser` (usuário + preferências + revogação de tokens) não abrem mais
  transação própria. `DefaultPreferencesParams` continua como fonte única dos defaults.
- `RefreshTokenController` — `Create`, `FindByID`, `Extend`, `Revoke`, `RevokeAll`.
- `UserPreferencesController` — `CreateDefault`, `FindByUserID`, `Update`, `SoftDelete`.
- `AuthController` — `HandleGoogleCallback` e `RefreshAccessToken` abrem `WithTransaction`
  só em volta das gravações (I/O do Google fora); `RegenerateFromClaims` recebe `q`.
- `interfaces.go` — todas as assinaturas atualizadas com `q`.

### Rotas e middleware

- `middlewares/auth.go` e os endpoints de escrita (`logout`, `invalidate`,
  `invalidate-all`, `update-preferences`) recebem o `TransactionRunner` injetado e abrem
  a transação, passando `q` aos controllers.
- `main.go` cria o `WithTransaction` real (ligado ao pool `*sql.DB`) e injeta em tudo.

### Outras correções da revisão (já aplicadas nesta leva e na anterior)

- `findOrCreateUser` usa `errors.Is(err, ErrUserNotFound)` em vez de comparação direta.
- `SoftDeleteUser` passou a revogar as sessões do usuário (antes só removia usuário +
  preferências).
- `main.go`: `JWT_SECRET_KEY` vazio agora aborta o boot; `API_PORT` é respeitado.
- `tests/utils/db.go`: `SetMaxOpenConns(1)` — `:memory:` é por-conexão; sem isso a
  transação poderia ler de um banco vazio diferente.
- Removido dead code (`seedSession`, `GenerateExpiredTestAccessToken`,
  `extractUserIDFromToken` duplicado).
- Comentário na migração de preferências explicando o UUID v4 do backfill (exceção
  consciente).

### Testes (filosofia das três camadas preservada)

- **Unitários**: recebem o `fakeTxRunner` (`func(ctx, fn) { return fn(nil) }`) →
  continuam puros, sem banco nem serviço de pé.
- **Integração / E2E**: recebem o `WithTransaction` real ligado ao banco em memória.
- Novo `tests/integration/api/auth/transaction_test.go`:
    - `RollsBackOnError` — cria usuário e força erro depois → usuário **não** persiste
      (prova a prevenção de órfão).
    - `CommitsOnSuccess` — usuário + preferências persistem juntos.
    - `DuplicateReturnsError` — caminho de falha de gravação por violação de UNIQUE.
- Todos os pacotes verdes; build, `go vet` e `gofmt` limpos.

## Decisão de design documentada

A regra está em `conventions.md` (seção "Transações"): controllers são intermediários
que nunca finalizam; `WithTransaction` é o único responsável por commit/rollback; toda
manipulação de banco passa por ele.
