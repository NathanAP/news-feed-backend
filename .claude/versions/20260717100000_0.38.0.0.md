# 0.38.0.0 — Filtragem e paginação em SQL

Fecha a dívida que a 0.37 (Postgres) deixou explicitamente anotada como "fora do escopo, candidato
natural logo depois": as listagens filtravam e paginavam **em Go**.

## O problema

Os quatro endpoints de listagem seguiam o mesmo padrão: o controller trazia **todas** as linhas
ativas da tabela, o handler filtrava com `strings.Contains` e o `pagination.Paginate` fatiava o slice
em memória. Com o SQLite isso era uma escolha defensável; com o Postgres virou desperdício puro —
para servir 20 notícias a aplicação materializava a tabela inteira, e o `total_count` era um `len()`.

O próprio comentário do pacote registrava a dívida: "Slicing happens in memory (...) revisit with SQL
LIMIT/OFFSET if the dataset outgrows this, e.g. after Postgres".

## O que mudou

**Contrato da API: inalterado.** Mesmos query params, mesmo envelope `{ docs, pagination }`, mesmos
status codes. O client e o Bruno seguem intactos — a única exceção é o filtro `name` de sources, que
é novo (ver abaixo), e a ordem de notícias empatadas no `created_at`, que agora é estável.

### Pacote `pagination`

- `ParseParams` inalterado (ainda normaliza/clampa `page` e `page_size`).
- **Novo** `Params.Limit()` / `Params.Offset()`: o que a query usa no `LIMIT`/`OFFSET`.
- **Novo** `BuildResponse(docs, totalCount, params)`: monta o envelope a partir do total **do banco**.
- **Removido** `Paginate[T]` (fatiava em memória). Sem call sites = código morto.
- `Meta.TotalCount` virou `int64` (é o que o `COUNT(*)` do Postgres devolve; converter para `int` seria
  perda gratuita de tipo).

### Queries (`sqlc/queries/`)

Cada listagem ganhou filtros opcionais + `LIMIT/OFFSET`, e uma query `Count*` irmã com **os mesmos
filtros** (elas ficam coladas no arquivo, com um comentário dizendo que precisam andar juntas):

| Endpoint | Filtros | List | Count |
| --- | --- | --- | --- |
| `GET /v1/articles` | `url` | `ListArticles` | `CountArticles` |
| `GET /v1/sources` | `url`, `name` | `ListSources` | `CountSources` |
| `GET /v1/feeds` | `name` | `ListFeedsByUser` | `CountFeedsByUser` |
| `GET /v1/feeds/{id}/articles` | `is_read`, `period_starting_at`, `period_ending_at` | `ListArticlesByFeedForUser` | `CountArticlesByFeedForUser` |

Detalhes das decisões:

- **Filtro opcional = `sqlc.narg`**: `(sqlc.narg(x) IS NULL OR <teste>)`. Um filtro ausente chega como
  `NULL`, não como zero value — passar `""` filtraria por "contém string vazia" e passar `false`
  filtraria por `is_read = false` silenciosamente. O mapeamento vive num lugar só
  (`controllers/filters.go`, helpers `nullableString`/`nullableBool`/`nullableTime`).
- **`strpos(lower(a), lower(b)) > 0`, não `ILIKE '%...%'`**: é exatamente o que o
  `strings.Contains(strings.ToLower(...))` fazia, e não deixa `%`/`_` do usuário virarem curinga.
  Nenhum dos dois usa índice (curinga à esquerda); se um dia precisar de busca indexada, o caminho é
  `pg_trgm` + GIN. Há teste de integração provando que `?url=%` devolve vazio em vez de tudo.
- **Duas queries, não `COUNT(*) OVER()`**: a janela entrega o total *nas linhas*, e numa página fora do
  range não há linha nenhuma — o total sumiria, quebrando a regra do `PROJECT.md` ("página 5 de 4"
  devolve `actual_page: 5`, `total_pages: 4`). O custo é um `total_count` possivelmente off-by-one por
  um instante sob insert concorrente (`READ COMMITTED`); decidido junto que é aceitável.

### Ordenação: desempate por `id` (bug latente)

Todas as listagens passaram de `ORDER BY created_at DESC` para `ORDER BY created_at DESC, id DESC`.

O `LIMIT/OFFSET` expôs um problema que a fatia em memória escondia: a CRON grava várias notícias no
mesmo instante, elas empatam no `created_at`, e o Postgres não garante ordem estável entre linhas
empatadas. Resultado: uma notícia podia aparecer na página 1 **e** na 2, e outra sumir das duas.

O `id` é UUIDv7 — carrega o timestamp nos bits mais significativos e é a PK (nunca empata). Então o
desempate torna a ordenação **total** (paginação consistente) e continua cronológico.

Verificado empiricamente: removendo o `id` do `ORDER BY` e regerando o sqlc, o teste
`TestIntegration_ListArticles_PaginationIsStableAcrossTiedTimestamps` falha com "every article must
appear exactly once across the pages". Com ele, passa.

### `ListAll` separado do `List` (decisão que surgiu na execução)

A CRON (`DiscoveryRunner`, que varre as sources ativas) e os scripts de `cmd/seed` também chamavam
`List` — e precisam de **todas** as linhas, não de uma página.

Ganharam queries e métodos próprios, sem `LIMIT`: `ListAllSources`, `ListAllArticles`,
`ListAllFeedsByUser` (+ `ListAll` nos controllers e interfaces). A alternativa — passar um `page_size`
grande o bastante "pra caber tudo" — seria uma gambiarra esperando o volume crescer para virar bug
silencioso (a varredura pularia sources). A separação também deixa explícito quem é batch e quem é
HTTP: **handler usa `List` (sempre paginado), batch usa `ListAll`**.

### Filtro `name` em sources (lacuna doc × código)

O exemplo do `conventions.md` prometia `GET /v1/sources?url=...&name=...`, mas o `name` nunca foi
implementado — o campo existe desde a 0.30 e o endpoint de listagem só filtrava por `url`. Como a
query estava sendo reescrita de qualquer forma, o filtro entrou junto. `url` e `name` são
independentes e se combinam com AND.

### Controllers

`List` passou a receber um struct de filtro e devolver `(rows, total, error)`:

```go
List(ctx, q, filter ListSourcesFilter) ([]db.Source, int64, error)
```

Os structs (`ListArticlesFilter`, `ListSourcesFilter`, `ListFeedsFilter`, `ListFeedArticlesFilter`)
vivem em `services/controllers/filters.go`. O `userID` de feeds continua **argumento obrigatório**, não
campo do filtro: um feed só é visível ao dono, e isso não pode depender de alguém lembrar de preencher
um campo opcional. As duas queries (página + count) rodam na mesma transação do handler.

### Handlers

Perderam código: sumiram os `applyFilters` e os loops de filtro. Restou parsear/validar a query (o 400
de `is_read` inválido e de data inválida continua no handler) e montar o envelope.

## Testes

O papel de cada camada mudou, e isso é o ponto mais importante da versão para quem for mexer aqui
depois:

- **Unitário**: já não pode testar filtragem (quem filtra é o SQL). Passou a provar que o handler
  **repassa o filtro certo** — inclusive que `?is_read=false` chega como `*bool` apontando para `false`
  e não como "sem filtro", e que as datas chegam normalizadas para UTC. Isso casa com o `PROJECT.md`,
  que define o unitário como "dados que chegam sejam validados corretamente".
- **Integração**: onde a filtragem real é provada, contra um Postgres de verdade. Arquivos novos:
  `tests/integration/api/{articles,sources,feeds}/list_filters_test.go`.

Cobertura nova relevante: substring case-insensitive; curingas tratados literalmente; filtro aplicado
**antes** da paginação; soft-deleted fora do `total_count`; `url`+`name` combinando com AND; janela de
data inclusiva nas duas pontas; bound em offset não-UTC convertido; filtro nunca cruzando usuários (e
o total também escopado); e a estabilidade da paginação sob `created_at` empatado.

Para forçar `created_at` idêntico (estado que a API não produz, pois é `CURRENT_TIMESTAMP`), o
`setupIntegrationApp` de articles e feeds passou a devolver também o `*sql.DB` cru.

Testes de integração que chamavam `queries.ListArticles(ctx)` para conferir o que foi gravado passaram
a chamar `ListAllArticles` — eles querem o conjunto todo, não uma página.

`task ta` (unit + integração + e2e): verde.

## Como testar

```bash
task dbs      # sobe o Postgres
task ls       # sobe a API
task sdfull   # popula e imprime um token
```

No Bruno (ou curl), com o token:

- `GET /v1/sources?name=wiki` — filtro novo desta versão.
- `GET /v1/sources?url=globo&name=esporte` — os dois filtros combinando com AND.
- `GET /v1/articles?page=1&page_size=2` e `?page=2&page_size=2` — nenhuma notícia deve repetir entre
  as páginas (era o bug do empate).
- `GET /v1/articles?page=999` — `docs: []`, `actual_page: 999`, `total_pages` real, sem erro.
- `GET /v1/articles?url=%25` — deve devolver vazio (com `ILIKE` devolveria tudo).
- `GET /v1/feeds/{id}/articles?is_read=false&period_starting_at=2026-07-01T00:00:00Z`.

Para ver o SQL de verdade, `VERBOSE_MODE=true` nos logs ou o pgAdmin4 em `:5050`.
